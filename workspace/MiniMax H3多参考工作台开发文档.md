# MiniMax H3 多参考工作台开发文档

## 0. 当前产品边界与上传改造范围

MiniMax H3 是当前唯一继续维护的画面生成路线。普通数字人生成和 LTX 对口型均已废弃；它们的
代码、迁移、任务和素材暂作历史兼容与追溯保留，但不再进入新功能、上传优化、服务器迁移、发布
或验收范围。账号、MiniMax 声音、H3 调度、字幕/BGM、后期、成果库等 H3 仍在使用的公共能力
不属于废弃范围。

当前上传问题只处理 H3 所需的参考人物图和参考视频，并按来源分成两个合同：

- H3 网页直传：浏览器图片、视频经 `/api/h3-page/assets` 上传，并用
  `/api/h3-page/assets/lookup` 恢复结果；云端分块落盘、分块计算摘要，格式验证只读取前 32 字节。
- H3 工作台上传：JYD 图片、视频经 `/api/workbench/h3-assets` 上传，并用
  `/api/workbench/h3-assets/lookup` 查询。第一阶段保持原始字节，`transport_profile=original-v1`，
  `source_sha256 == transport_sha256`；请求体按不超过 1 MiB 的块流式发送，禁止
  `Path.read_bytes()` 和整包 `b"".join(...)`。
- 两条入口分别记录 `source_channel=h3_web` 与 `source_channel=h3_workbench`，并记录素材角色、原始
  大小、传输大小、耗时、结果和幂等命中；不得记录令牌、绝对路径或文件内容。
- 第一阶段已在本地代码完成，只解决整文件内存复制、重复上传和可观测性；工作台视频编码、图片尺寸/质量参数需要
  用 H3 画面效果做 A/B 后再冻结版本。当前浏览器预览用的 720p H.264 代理不是上传合同，不能
  未经验证直接冒充 H3 输入。

## 1. 文档目的

本文件是 H3 多参考工作台的跨项目产品和技术依据。H3 现为唯一继续维护的画面生成链路；
`runninghub_mvp` 承担云端 H3 接口和调度，JYD 承担正式本地输入及后期，数字人网站仍可保留
H3 网页直传入口。`8792` 只保留为技术验收页，不是生产入口。

第一版只开放 H3 全参考生成（Ref2VA），面向单人物中文口播：每条脚本行选择自己的参考视频，
由同一行拆出的全部 H3 分段继承该视频的人物神态、动作习惯、构图和背景风格；用户可再提供
整批共用的少量人物图片加强身份约束。系统把分段音频作为 H3 多参考条件，由模型共同生成新
视频及其同步音轨；最终成片必须保留这组 H3 原生音画。MiniMax 输入音频和 raw cues 只用于
生成条件、冻结原稿、自动分段和来源审计，不能在后期覆盖 H3 解码音轨。

本文件冻结稳定业务合同；具体 RunningHub 工作流、节点 ID、模型文件和能力上限属于可替换的
适配器版本。未来 H3 工作流自带循环、续写或更强首帧条件时，不应修改工作台、项目或 JYD 的
核心输入合同，只替换适配器和连续性策略。

## 3. 已确认的产品决策

1. H3 是唯一继续维护的画面生成链路，不与已经废弃的普通数字人或 LTX 共用远端任务状态。
   H3 网页直传与 JYD 工作台上传必须使用不同来源标识和传输策略；`8792` 只用于技术验收。
2. 第一版只开放 Ref2VA，不做 H3 文生视频、首尾帧或视频编辑的通用入口。
3. 参考视频属于脚本行/生成项目，不属于整批唯一输入。不同脚本行可以选择不同参考视频；同一
   行只上传一次，prepare 阶段按固定 3 秒边界切成无音轨动作片段，最后不足 3 秒的尾段仍保留，
   再自动均衡分配给该行音频分段。0～1 张用户图时参考视频仍提供完整画面依据和表演；2 张以上
   时参考视频提供表演，并由系统从原始视频抽取主画面。
4. 云端独立工作台仍支持整批共用 `0～4` 张同一人物图片；JYD 正式入口改为逐行人物图：直接
   读取该行现有图片分配结果，每行只提交 1 张，多个不同人物不得再混入同一扁平列表。JYD 的
   `loop` 按行依次循环，`count` 允许一张图连续对应多行，不再维护第二套“H3 人物图”勾选状态。
5. 当前 H3 工作流最多使用 6 张参考图。2～4 张用户图时，系统从每行参考视频 0.5 秒处抽帧
   （失败回退首帧）占 `<Picture 1>`，用户图顺移到 `<Picture 2>`～`<Picture 5>`；连续模式
   上一段尾帧固定占 `<Picture 6>` / `ref_images.ref_image_5`。
6. 0～1 张用户图不自动抽帧：0 图只用视频，1 图只补充人脸身份。所有图片按实际数量连接，
   不使用示例图、空白图、透明图或重复图片凑数。
7. 第一版生成页接收用户已准备好的完整成品音频和对应原稿，不在该页面调用 MiniMax TTS。
   系统用 FunASR 把原稿对齐到音频后自动规划 H3 分段；用户不逐段手填文案。
8. 节点 `105` 的分辨率参数必须按任务动态写入。默认画幅为
   `9:16 (Portrait Widescreen)`、`megapixels=1.0`、`multiple=32`；画幅和 megapixels
   可由用户修改并在行启动时冻结，`multiple` 第一版保持 32。
9. 节点 `84.value` 不要求用户逐段手填。系统用媒体探测器读取当前分段音频真实时长，默认
   写入 `audio_duration_seconds + 0.1` 秒，再由节点 `92` 换算到 H3 有效帧网格。若换算后超出
   当前适配器上限，必须重新规划更短分段，不能静默裁掉语音。
10. H3 请求时长硬范围为 4～15 秒，第一版音频分段目标范围为 8～12 秒，优先在自然标点和
    停顿边界切分；最终合法性以“音频真实时长 + 0.1 秒余量”经过节点 `92` 量化后的结果为准。
11. 正式工作台支持 `loop_anchor`（首尾同图）、`fast`（快速并行）和 `soft_chain`（尾帧软连续）
    三种模式，默认 `loop_anchor`。该模式至少需要 1 张人物图，并始终把用户有序选择的第一张图
    作为 `<Picture 1>`，同时约束每段第一帧和最后一帧；不会把参考视频自动抽帧插到其前面。
12. 当前工作流没有独立 first-frame/start-image 条件，因此尾帧只能作为普通 Ref2VA 图片进行
    软参考，不能宣称逐像素首帧锁定。
13. 未来工作流自带循环或续写节点时使用 `native_loop` 策略，不再由本地逐段抽尾帧。
14. H3 成功结果必须进入 JYD；最终成片使用 H3 解码音轨。字幕以 H3 实际输出分段时长建立
    宽窗口，再用 FunASR 将冻结原稿对齐到 H3 成片语音；输入 raw cues 只做分段和审计。
15. 第一版不接 SeedVR2。
16. H3 直接复用现有多账号/双池基础设施的账号快照、原子选号、并发槽位、重试、取消和费用
    保护，但 H3 自身只有一个付费阶段，应表现为独立 H3 执行池，不虚构第二个处理阶段。
17. 未经用户明确授权，不发起真实 MiniMax、RunningHub 或剪映付费任务，不部署生产，不修改
    云端账号数据库。
18. H3 是否对某个登录用户开放由数字人网站“用户管理”中的独立权限控制，不得借用双池总开关、
    管理员身份或双池测试授权。RunningHub 资源池只配置执行账号的 Key、Workflow ID、密码、
    实例、并发和成员范围；两个层次必须分离。
19. 2026-08-28 起，老数字人网页 `/generate/batch` 的 H3 区域允许批次级人工总体 Prompt 完整
    覆盖。留空继续使用系统六段式编译；填写后所有自动分段原样使用同一文本，`user_direction`
    不再追加，系统也不再自动写入分段台词或默认身份、音频和衔接约束。该能力必须明确提示风险，
    并在费用预检时冻结文本、版本和摘要。

## 4. 总体架构

`h3_video_workbench/` 保留为适配器、专项测试和技术验收项目。当前 H3 有网页直传与 JYD 本地
工作台两种输入来源，二者都进入 `runninghub_mvp` 的 H3 云端合同，结果由 JYD 完成后期；浏览器
和本地工作台都不接触 RunningHub Key。

```text
数字人网站 /generate/batch (h3_web)
  或 JYD /app/new/generate (h3_workbench)
  -> 上传 H3 对应原稿、参考视频、人物图和已审核声音引用
  -> FunASR 对齐冻结原稿，生成 raw cues
  -> H3 自动分段和 Prompt 编译
  -> runninghub_mvp H3 云端接口
       -> H3 账号池快照和原子选号
       -> 上传当前脚本行的参考视频、分段音频和有效图片
       -> H3DynamicGraphBuilder
       -> RunningHub raw-workflow 提交
       -> 查询、取消、下载和结果归档
  -> 保留 H3 完整输出、连续性尾帧抽取和原生音画合并
  -> 交给 JYD 字幕/BGM/语义视觉/封面/变体/成果库
  -> 拆出 H3 权威音频 + 从 0 秒开始的静音 base_video
  -> 以 h3.jyd_handoff.v2 合同回填原 JYD ProjectItem
  -> JYD 现有 4B 字幕/BGM/语义视觉/封面/变体/成果库整批处理
```

当前 `8792 -> 每行新建一个 JYD 项目` 的实现只用于验证底层合同。正式集成不得继续为每行创建
孤立项目，而应把 H3 结果和版本历史写回发起任务的原 `ProjectItem`；同一 JYD 批次中的多行
必须继续留在同一个项目内。

通用层不得知道 H3 节点 ID。所有工作流 JSON、节点映射、动态删图规则、Prompt 结构、时长
取整和输出定位都属于 H3 适配器。

- 每个 item 的 `script_text` 是该行字幕、分段、内容分析和语义视觉的权威文本；
- 批次默认分辨率为 `9:16 + 1.0MP + multiple 32`；用户可批量应用画幅和 megapixels，也可
  对单行覆盖。费用确认时保存合并后的有效值，而不是在 Worker 运行时重新读取页面默认值；
- `generation_tail_seconds` 默认 0.1，属于适配器可版本化参数，不是用户逐段输入；
- `prompt_override` 仅由老网页批次级高级输入使用；非空时以
  `h3.prompt.manual-override.v1` 原样覆盖每个分段的完整 Prompt，并使 `user_direction` 归一为空；
- `user_direction` 在没有人工完整覆盖时仍是受控补充，不能注入六段结构或引用标签；
- `continuity_mode`、分辨率、参考素材摘要、Prompt 版本、音频版本和适配器版本在费用确认时冻结；
- 任何 API 都不得向浏览器返回 RunningHub Key、访问密码或完整执行凭据。

独立页面不得要求普通用户手工复制 MiniMax 批次 ID、行 ID 和生成版本。云端提供账号隔离的
`h3-audio-sources` 安全摘要，只列出音频和 raw cues 都存在的来源，包括待审核音频和已有审核
记录的 `SUCCESS` 历史音频；历史音频可重复绑定新的 H3 批次，且不得重新合成、重复产生 MiniMax
费用或改写原审核记录。选择后自动带出只读冻结原稿和版本。本地试听通过受登录保护的代理完成，
试听临时文件在响应结束后删除，访问令牌不进入浏览器。

## 6. 自动语音与分段合同

### 6.1 权威来源

默认输入是项目根据完整脚本生成并审核通过的一条 MiniMax 语音及其 raw cues。正常情况下从
同一份 raw cues 同时确定：

- 原脚本字符左闭右开区间；
- 原音频起止时间；
- 精确 `segment_text`；
- 分段音频文件；
- 分段时长和稳定 `segment_id`。

MiniMax 可能把超过 H3 请求上限的完整音频只返回成一个 raw cue。此时不得把 cue 当作不可拆
单元，也不得按字符比例盲切。JYD 正式入口必须在本机费用预检阶段复用或调用 FunASR，把识别
token 对齐到冻结原稿，再提交 `jyd.h3-safe-cut-alignment.v1`。该合同同时绑定冻结原稿 SHA-256、
完整 MiniMax 音频 SHA-256、声音批次、行 ID 和生成版本；云端逐项校验后只用字词时间戳在该 cue
内寻找标点/字词安全切点，不得依赖生产服务器本机的 `127.0.0.1` ASR。旧客户端没有提交合同时
继续保留原云端兼容回退，但它不是 JYD 生产链路。每段文字仍按字符区间逐字截取冻结原稿，ASR
不能改写、补字或删字；原 raw cues 继续作为来源审计保留。对齐不足或绑定不一致时必须在付费前
失败。

H3 成片进入 JYD 后还会对 H3 解码音轨再次运行 FunASR，但那一步只负责最终成片字幕时钟，
与生成前修复过长 raw cue 的切点定位属于两个独立阶段。

### 6.2 分段规则

1. 节点 `84` 的 H3 请求时长硬范围为 4～15 秒；分段音频目标范围为 8～12 秒。
2. 优先级依次为：句号/问号/感叹号/真实换行、分号/冒号、逗号、最后的安全字符边界。
3. 每段音频切出后必须用媒体探测器读取真实编码时长，不只相信 raw cues 计算值。节点 `84`
   写入 `audio_duration_seconds + generation_tail_seconds`，默认余量为 0.1 秒。
4. 节点 `92` 使用当前工作流公式把节点 `84` 的秒数换算为 24fps 且满足 H3 帧网格的帧数。
   分段器必须用同一公式做生成前预检；量化结果低于最小时合并/调整边界，超过上限时继续拆分。

   ```text
   base_frames = max(5, round(requested_generation_duration_seconds * 24))
   quantized_frame_count = base_frames + (5 - (base_frames % 17)) % 17
   effective_generation_duration_seconds = quantized_frame_count / 24
   ```

   0.1 秒是写入节点 `84` 前的请求余量，不承诺最终 H3 文件只多出精确 0.1 秒。节点 `92`
   还可能为对齐帧网格追加 0～16 帧。最终必须保留 H3 返回的完整音画，不能按输入分段音频
   时长机械裁尾，更不能从中间删除余量。

5. 尾段太短时优先并入上一段；不得创建服务商必然拒绝的短段，也不得为满足上限裁掉台词。
6. 切点优先落在 raw cues 映射出的自然停顿附近；raw cue 自身超过上限时，使用 FunASR 对齐
   到冻结原稿后的标点/字词时间边界继续拆分。两种路径都不能重复或漏掉原脚本字符。
7. 语音停顿配方尚未实现前，不得把 `语音标点停顿配方开发文档.md` 描述成已上线能力；
   实现后 H3 只消费冻结音频和 raw cues，不重新编译停顿。
8. 分段变化必须产生新的分段计划摘要并使对应 H3 结果失效，但不得删除历史付费结果。当前
   实现版本为 `h3.segment.minimax-cues+funasr.v2`。

建议分段记录至少包含：

```json
{
  "segment_id": "stable-id",
  "segment_index": 0,
  "script_char_start": 0,
  "script_char_end": 20,
  "segment_text": "精确台词",
  "audio_start_us": 0,
  "audio_end_us": 9000000,
  "audio_duration_us": 9000000,
  "generation_tail_seconds": 0.1,
  "requested_generation_duration_seconds": 9.1,
  "quantized_frame_count": 0,
  "effective_generation_duration_seconds": 0,
  "audio_sha256": "...",
  "prompt_sha256": "...",
  "previous_anchor_asset_id": null
}
```

## 7. H3 Prompt 编译

### 7.1 权威格式

Prompt 必须使用个人技能目录中的官方 `h3-prompt-writing` skill。Ref2VA 固定六段顺序为：

```text
subject_definitions
summary
retention_analysis
detailed_description
overall_soundscape
non_diegetic_music
```

说明段使用英文；真实台词保留原语言并放入 `<d>[Chinese] ...</d>`。引用标签必须和本次实际
有效素材顺序一致。

### 7.2 固定表现目标

当前用户确认的默认口播表现配置包括：

- 保持人物身份、脸型、五官比例、发型、服装、体态和自然小巧嘴型；
- 参考视频提供人物自然神态、头肩上身运动、手势习惯、动作幅度和节奏；
- 保持参考视频的背景、空间、光线、肤色渲染、构图和制作质感；
- 人物成熟、自信、从容、积极、有能量和自然权威感，但不戏剧化、不直播叫卖、不故意攻击；
- 单一连续镜头、稳定机位，不引入与参考视频冲突的推拉摇移或镜头尺寸跳变；
- 根据当前完整分段台词生成新动作，不复制、循环、镜像或机械延长参考视频原动作；
- 嘴型准确、流畅、真实，但不得为音素夸张扩大嘴宽、唇厚或下颌开合；
- 输入音频为完整台词音轨，不增加突出环境声或无关音效；
- `non_diegetic_music: N/A`。

正式模板应压缩重复否定句，但不能丢失这些优先级。官方指南建议生成类
`detailed_description` 通常控制在约 350～500 个英文词；不得简单把网页版长 Prompt 原样复制
到每一段。

### 7.3 动态变量

```text
{{SUBJECT_SOURCE_DEFINITION}}
{{REFERENCE_VIDEO_ROLE}}
{{IDENTITY_PICTURE_LABELS}}
{{CONTINUITY_PICTURE_DEFINITION}}
{{SEGMENT_TEXT}}
{{SEGMENT_DURATION}}
{{SEGMENT_INDEX}}
{{SEGMENT_COUNT}}
{{USER_DIRECTION}}
```

身份图片只用于定义人物时应在 `<Subject 1>` 内引用，不单独创建无实际作用的 Picture 条目。
上一段尾帧承担开场姿态和构图参考时，才创建独立 `<Picture 6>`；该标签与人物图片实际数量
无关，并固定映射到工作流第六图槽。人物图片只作为 `<Subject 1>` 的来源，不单独建立 Picture
条目。

`h3.prompt.ref2va.v5` 按官方 Ref2VA 的最少充分 ontology 重建四个跟踪单元：`<Subject 1>` 是
人物，人物图片只提供稳定脸部身份，`<Video 1>` 提供发型、服装、配饰、体态和不包含具体原始
动作序列的抽象表演语言；`<Subject 2>` 是来自视频的环境；`<Video 1>` 只定义景别、构图、相机
行为、运动节奏、时序组织和人－相机－环境空间关系；`<Audio 1>` 是完整最终音轨。Retention
固定为 Subject 1/2 `fully_preserved`、Video 1 `partially_preserved`、Audio 1
`fully_copy`。连续段额外加入 `<Picture 6>: partially_preserved`，summary 增加
`keyframe completion`。`overall_soundscape` 明确不增加环境声、音效、其他声音或音乐。

### 7.4 音频语义

Prompt 使用：

```text
[reference generation + audio reuse]
<Audio 1>: fully_copy - <Audio 1> is reused 1:1 as the complete spoken audio track.
```

并要求 `<Subject 1> (S1)` 物理开口说出精确 `segment_text`，嘴型遵循 `<Audio 1>` 的每个词、
停顿和节奏。不得误写成只参考音色的 `audio reference`。

`fully_copy` 是给模型的内容与节奏意图，不等于服务端一定逐采样复制输入信号。节点 `364` 解码
出的 H3 音频与节点 `365` 解码出的视频是模型共同生成并同步的一组结果，节点 `387` 已将两者
正确封装。工程层必须保留这组 H3 原生音画，禁止再把输入 MiniMax 音频覆盖到输出视频上。

### 7.5 用户补充入口

普通路径继续只提供附加画面/动作方向，编译器保留人物一致、物理开口、音频复用、无额外音乐、
无可见字幕和稳定镜头等固定规则。老数字人网页另有显式“人工总体提示词（完整覆盖）”高级输入：

- 留空时仍走上述系统编译路径；
- 非空时每个自动分段把同一份人工文本原样写入节点 `83.text`，不再自动追加分段台词、
  `user_direction` 或任何六段式固定规则；
- 页面必须提醒用户自行保证引用标签、台词、音频复用和衔接约束正确；
- 人工文本最多 7000 字符，保留换行，版本固定为 `h3.prompt.manual-override.v1`；
- 文本及其 SHA-256 在费用预检时冻结，确认、失败重试、人工重生成和 soft-chain 后段解锁必须
  使用同一快照，不能重新读取页面或回退默认模板。

## 8. 动态 RunningHub 工作流

### 8.1 为什么不能只靠 nodeInfoList

`nodeInfoList` 用于替换已发布图中现有节点字段。它可以修改图片、视频、音频、Prompt、时长、
分辨率和 Seed，但不负责安全地增删 ComfyUI 连接。未传某个图片节点时会继续使用工作流默认
值；已连接的标准 `LoadImage` 留空则会因图片不存在而校验失败。

因此正式工作流不得保存示例 JPG、`example.png` 或空白占位图，也不得通过不传 nodeInfoList
把默认图误当成“无图片”。

### 8.2 正式提交策略

H3 使用 RunningHub 支持完整自定义 workflow JSON 的高级接口，按次提交运行时构造的
API-format 图。当前项目固定 workflowId 的 v2 客户端保持不变；为 H3 新增独立
`raw-workflow` 提交策略和响应解析，不得改变数字人、LTX 或 SeedVR2 的既有提交路径。

```text
受控 H3 API 模板
  -> 校验模板版本和 SHA-256
  -> 写入本次实际素材与 Prompt
  -> 按实际图片数裁剪图片分支
  -> 校验所有引用和输出节点
  -> 序列化完整 workflow JSON
  -> RunningHub 高级 raw-workflow 提交
```

不接受浏览器或普通用户上传任意工作流 JSON。动态图只能来自仓库中管理员审核过的模板，构造器
只允许修改白名单字段和已知图片分支，防止任意节点或路径注入。

### 8.3 当前基线节点映射

根据 2026-08-22 提供的六图 API 导出：

| 业务输入/输出 | 节点与字段 |
| --- | --- |
| Prompt | `83.text` |
| H3 请求时长秒数 | `84.value = 分段音频真实时长 + 0.1` |
| 帧数换算 | `92`，按 24fps 和 H3 帧网格量化 |
| 画幅 | `105.aspect_ratio`，默认 `9:16 (Portrait Widescreen)` |
| 像素量 | `105.megapixels`，默认 `1.0` |
| 分辨率倍数 | `105.multiple`，第一版固定 `32` |
| 图片加载 | `97`、`101`、`132`、`170`、`174`、`178` |
| 图片缩放 | `99`、`102`、`129`、`168`、`172`、`176` |
| Ref2VA 条件节点 | `108` |
| 参考视频 | `135.video` |
| 参考音频 | `138.audio` |
| Seed | `243.noise_seed` |
| 视频/音频采样 | `247` |
| 视频解码 | `365` |
| H3 音频解码 | `364` |
| 最终 MP4 | `387`，动态 API 图必须强制 `save_output=true` |

输出选择必须明确要求节点 `387` 且 `outputType=mp4`，不能把 PreviewImage 当作最终结果。下载的
官方 API 图中节点 `387.save_output=false` 只产生预览，不会进入 RunningHub 高级输出文件列表；
适配器提交前必须在本次动态副本中改为 `true`，并由结构测试断言，不能修改用户导出的原始文件。

当前 API 图还包含未通往最终采样输出的 Ref2VA 模型分支 `9 -> 396 -> 392 -> 187`；实际采样
模型链为 `8 -> 395 -> 391 -> 186`。这是现有工作流事实，实施前必须通过少量真实测试验证，
不得在没有证据时擅自删除、换线或宣称它是错误。

### 8.4 图片分支动态构造

逻辑输入：

```python
identity_images = (
    [frame_at_0_5s_or_first_frame, *user_reference_images]
    if len(user_reference_images) >= 2
    else user_reference_images
)
```

约束：

- `user_reference_images` 为 0～4；
- `optional_previous_anchor` 为 0 或 1；
- `effective_images` 为 0～6；
- 2～4 张用户图时，自动主画面和用户图按实际数量从 `ref_image_0` 到 `ref_image_4` 紧密排列；
  0～1 张用户图直接按原顺序连接；soft-chain 尾帧始终映射
  `ref_image_5`，中间未使用的人物槽保持不存在；
- 未使用的 `ref_images.ref_image_N`、LoadImage、缩放和 PreviewImage 节点从本次完整 workflow
  JSON 中移除；
- 不保留中间空洞，不复制图片补位；
- 动态构造后必须验证所有节点引用存在、最终输出可达、无未授权节点类型。

2026-08-22 的结构探针已经确认：

- 0 图 API 图的节点 `108` 不含任何 `ref_images.*`；
- 1 图 API 图只含 `ref_images.ref_image_0 -> 99 -> 97`；
- 两者都没有悬空节点引用，最终节点 `387` 的主链完整。

正式实现不需要发布 0～6 七套工作流。多版本 workflowId 只作为 RunningHub 高级 raw-workflow
接口不可用时的显式回退方案，不能作为默认架构。

### 8.5 模板版本化

每个任务至少冻结：

- `workflow_template_id`；
- `workflow_template_version`；
- `workflow_template_sha256`；
- `dynamic_graph_sha256`；
- `prompt_template_version`；
- `prompt_sha256`；
- `adapter_version`；
- 实际执行账号 ID 和提交协议版本。

工作流更新只影响新任务。运行中和历史任务继续使用其冻结版本；不得因默认模板更新而迁移或
重提已付费任务。

## 9. 连续性策略

### 9.1 loop_anchor

```text
effective_images = ordered_user_reference_images
Picture 1 = ordered_user_reference_images[0]
每段从 Picture 1 开始，并在最后可见帧回到 Picture 1
同一脚本 item 的各分段可以并行
```

这是新批次默认策略，至少需要 1 张人物图。用户选择顺序具有合同意义：第一张是人物、穿搭、
场景、构图以及每段首尾边界的主锚点；其余图片只补充同一人物身份。该模式不自动插入参考视频
抽帧，也不读取上一段结果。Prompt 使用 `h3.prompt.ref2va.loop_anchor.v2` 六段式 Ref2VA 模板；
它是生成约束，不宣称供应商提供逐像素硬关键帧能力。

### 9.2 fast

```text
effective_images = user_reference_images
同一脚本 item 的各分段可以并行
不读取上一段结果
```

`fast` 保留为视频/普通人物参考驱动的可选模式。JYD 后续的语义画面、B-roll 和接缝处理也可
用于遮挡分段跳变。

### 9.3 soft_chain

第一段：

```text
effective_images = user_reference_images
```

第二段及以后：

```text
effective_images = user_reference_images + previous_anchor
```

处理顺序：

1. 下载上一段 H3 结果；
2. 保留该段 H3 返回的完整原生音画；
3. 从完整 H3 视频的最后一个有效视频帧抽取图片；
4. 保存受管 `continuity_anchor` 资产及 SHA-256；
5. 把它作为下一段最后一张有效参考图片；
6. Prompt 将其描述为开场姿态、表情、构图和环境参考，不宣称真正硬首帧锁定。

同一行的分段形成依赖链，不能全并行；不同项目/行仍可跨账号并行。调度采用波次推进：每行
当前可运行段完成后立即释放槽位并推进下一段，不要求同一行始终使用同一 RunningHub 账号。

普通失败重试复用冻结尾帧，不重新生成上一段。用户主动重新生成某段时，工作台先调用
`POST /api/workbench/h3-segments/{segment_id}/regeneration/prepare` 展示受影响段号和预计付费
次数；再次明确确认后才调用 `.../regeneration/confirm`。目标段重新入队，依赖旧尾帧的所有
下游段进入 `WAITING_REGENERATION_DEPENDENCY`，新上游完成并产出尾帧后逐段解锁。历史结果
移动到任务 `history/regeneration-*` 目录并写入任务审计元数据，不物理删除；相同
`request_key + quote_token` 重复确认保持幂等，费用快照过期则拒绝提交。

### 9.4 native_loop

未来适配器若声明工作流内部支持循环、续写或原生连续生成，使用 `native_loop`：本地不抽取或
上传尾帧，由适配器把稳定批次输入映射到新工作流。JYD 仍只消费标准 H3 音画结果与冻结原稿。

### 9.5 默认值

建议配置：

```text
H3_DEFAULT_CONTINUITY_MODE=loop_anchor
H3_DEFAULT_GENERATION_TAIL_SECONDS=0.1
```

默认值只影响新建批次。每个批次冻结实际模式和余量；历史 `fast`、`soft_chain` 或 0.5 秒余量
任务不迁移、不重写，也不因新默认值自动重新提交。

## 10. RunningHub 多账号执行池

H3 复用 `dual_pool_v1` 已验证的安全原语：

- 管理员授权的候选账号 ID 快照；
- 费用确认时重新默认全选并至少保留一个账号；
- 原子选号与每账号并发槽位；
- 真实 API Key 指纹、余额安全摘要和健康状态；
- 远程任务始终绑定实际提交账号；
- 查询、取消、下载、恢复和看门狗使用原账号；
- 明确账号不可用才允许下次付费尝试换号；
- 下载失败、提交结果不明确或普通模型失败不得换号重提；
- 完整 Key、访问密码、请求体和第三方完整响应不进入浏览器或普通日志。

H3 新增独立账号能力配置，至少保存每个账号能否运行 H3 raw workflow、实例类型、并发上限、
安全备注和可选的私有工作流访问密码。访问密码使用 Fernet 密文保存，管理端只显示
“已配置/未配置”；Worker 提交前才解密并作为顶层 `accessPassword` 注入，不能进入 Prompt、
任务输入快照、浏览器响应或普通日志。它可以复用管理员现有账号集合，但不能把数字人工作流
ID 或 SeedVR2 工作流 ID 硬套给 H3。

管理员在既有 RunningHub 执行账号资源池内维护这组能力。新密码只接受一次写入并立即加密；
编辑时密码框留空必须保留原密文，只有勾选“清除已保存的 H3 工作流访问密码”才删除。审计日志
可以记录 `h3_access_password` 字段发生变化以及“是否配置”的布尔值，但不得记录明文或密文。

## 11. 任务状态、幂等和费用保护

建议 H3 段状态：

```text
PENDING
-> WAITING_DEPENDENCY        # soft_chain 等待上一段尾帧
-> UPLOADING
-> SUBMITTING
-> QUEUED / RUNNING
-> DOWNLOADING
-> NORMALIZING
-> SUCCESS
\-> FAILED / CANCELLED
```

幂等摘要至少覆盖：

```text
用户 + 批次 + segment_id + 分段音频 SHA-256
+ item_id + segment_text + Prompt SHA-256 + 当前脚本行参考视频 SHA-256
+ 有效图片有序 SHA-256 列表 + continuity_mode
+ 有效分辨率 + 生成余量 + 节点 84/92 量化结果
+ 动态 workflow SHA-256 + adapter_version + 实例类型
```

规则：

1. 相同摘要已有成功结果时复用，不创建付费任务。
2. 相同摘要已有远程任务时恢复轮询，不重复提交。
3. raw-workflow 提交响应不明确时保留占用和未知状态，不自动第二次提交。
4. 用户主动重生成必须显示费用，并创建新 attempt；不得覆盖历史 attempt。
5. 图片、视频、音频、脚本、Prompt、分段或连续性帧任一变化都形成新摘要。
6. 单段失败不删除其他成功段、音频、raw cues、JYD 配置或历史结果。
7. 真实调用前必须展示分段数、模式、候选账号、预计调用次数和当前是否存在可复用结果。
8. 失败、取消或下载失败的分段人工重试也必须先预览费用。普通失败/取消显示
   `provider_resubmit + 1` 次预计付费；已存在远端成功结果的 `DOWNLOAD_FAILED` 显示
   `download_only + 0` 次新调用。确认时校验状态快照，过期则拒绝；相同
   `request_key + quote_token` 重复确认保持幂等。
9. H3 分段允许显式取消：尚未提交的本地任务原子取消，已经提交的任务使用该尝试冻结的 H3
   执行账号、workflowId 和 raw-workflow 提交类型调用远端取消。取消请求必须带幂等键；取消后
   可按第 8 条重新预览并重试，不自动产生新费用。

## 12. H3 输出标准化与 JYD

原始工作流节点 `387` 已把节点 `365` 的 H3 解码视频和节点 `364` 的 H3 解码音频封装成同步
MP4。节点 `138` 的输入音频只是 H3 参考条件；把它再次铺回节点 `387` 的结果会改变语音起点，
直接破坏模型已经生成的口型同步。下载后必须：

1. 保留每段 H3 返回的完整音画，不按输入 MiniMax 分段音频时长裁切或补齐；
2. 保留原始 H3 结果用于排障，标准化结果也必须同时包含视频轨和 H3 音轨；
3. 按分段顺序无损合并 H3 音画；第一遍使用 concat stream-copy，第二遍按探测到的音频、视频
   起始时间分别归零，处理 AAC priming，同时避免重编码段内样本；
4. 保存完整 `h3_master` 作为可直接检查的最终音画对；
5. 为兼容 JYD 既有分轨时间线，从同一 `h3_master` 拆出静音 `base_video` 和一次性的 H3 权威
   PCM 音频，两者都从 0 秒开始，禁止基础视频与独立音轨重复发声；
6. 按每个 H3 实际输出视频时长建立能够逐字重建冻结原稿的分段字幕窗口；
7. JYD 对 H3 权威音频运行 FunASR，在对应 H3 分段窗口内得到字词时间戳，再把冻结原稿的语义
   字幕单位重新定时；不得使用输入 MiniMax raw cues 作为最终字幕时钟；
8. 通过 `h3.jyd_handoff.v2` 登记后进入现有 4B 字幕、BGM、语义视觉、封面、变体和成果库流程。

JYD 导入必须在一个 `BEGIN IMMEDIATE` 事务内完成项目、H3 权威音频、H3 分段字幕窗口、静音
`base_video` 和外部关联登记。同一账号、同一 `handoff_id` 的并发请求返回同一项目；任一步
失败整体回滚。导入前重新计算包含 `schema_version + project_id + source_segment_ids` 的摘要，
并校验字幕窗口拼接文本与冻结脚本一致，不能信任可被手工修改的本地清单字段。旧的
`h3.jyd_handoff.v1` 只为读取历史项目保留，不得作为新交接默认值。

输入 MiniMax 音频与 raw cues 可作为 provenance 保留，但不进入最终播放时间线。JYD 不需要知道
H3 的工作流节点 ID、账号 ID、动态图 JSON 或连续性实现。

接缝第一轮 A/B 使用直接硬切，便于观察真实跳变；不要先用长叠化掩盖问题。若
`soft_chain` 的首尾画面接近，正式策略优先硬切或 1～2 帧微叠化，避免人物重影。快速模式
是否复用现有 0.25 秒保时长叠化，应在真实样本后冻结为版本化 `seam_strategy`。

## 24. H3 随机片头杂音 ASR 自适应裁剪（2026-08-24）

2026-08-27 根据真实成片复核，当前暂时禁用这项裁切，但不删除实现。代码开关
`H3_HEAD_TRIM_ENABLED` 默认为 `False`；新生成分段以 0 秒裁切量保留完整 H3 原生音画，远程媒体
模式不创建 `h3_head_trim` 任务，本地模式也不调用片头 FunASR。生成前用于安全切段的
`h3_audio_alignment` 不受影响。当前合同为 `h3.output.generated-av-head-trim-disabled.v4`，用于
阻止新任务复用 v3 已裁切结果；以后重新启用时必须再次升级合同。下述定位、降级和同步裁切算法
作为保留实现继续维护。

真实样本表明 H3 每个独立生成分段的音轨开头可能随机出现短促异常声或带杂音的空白区，长度不
固定。后处理不再使用固定声学模板、能量阈值或 MiniMax 输入音频替换，而是复用现有 FunASR
时间戳与冻结分段原稿映射：

1. 从节点 387 原始 MP4 解码 H3 音轨供 FunASR 使用；
2. 要求原稿开头最多 3 个 spoken token 连续精确匹配，噪声即使被误转写，只要不对应原稿前缀
   就不会成为裁剪锚点；
3. 正常模式使用 `首字开始时间 - 40ms`，通过同一 ffmpeg filter graph 同步裁剪视频和音频并把
   两条时间轴归零；
4. ASR 服务异常、缺少时间戳、整体匹配失败或前缀不足时不返回任务失败，固定同步裁剪 300ms；
5. 不在尾部补回已裁掉的时长，不把 MiniMax 输入音频拉到 0 秒或覆盖 H3 权威音轨；soft-chain
   尾帧从裁剪后视频提取。

生产环境使用远程媒体模式时，第 1～4 步不得在服务器进程内直接调用 `127.0.0.1:18084`。
视频 Worker 下载节点 387 原始 MP4 后创建持久化 `h3_remote_asr_jobs`；固定电脑 Worker v4 以
`h3_head_trim` capability 主动领取、续租并回传裁剪决定。服务器严格校验模式、首词时间、40ms
预留量、匹配率和最大裁剪范围后才恢复 ffmpeg 后处理。节点断线由租约重领；远程 ASR 明确失败
才进入 300ms 降级，不重新提交已付费 H3。

输出合同为 `h3.output.generated-av-head-trim.v3`，裁剪模式、实际秒数、首字时间、匹配率、连续
前缀数和降级原因写入 `task.output_metadata.head_trim`。合同版本继续进入 H3 内容摘要，旧 v2
未裁剪结果不能被新任务误复用。2026-08-26 已补齐远程队列、租约、回传与恢复链的本地实现和
mock 回归，仍未部署生产，也未创建新的 RunningHub 付费任务。

同一张 `h3_remote_asr_jobs` 表也承载网页 H3 生成前的上传音频对齐。用户点击“计算分段与费用”
后，页面先为每条暂存音频创建 `h3_audio_alignment` action 并轮询；固定电脑下载音频、调用本机
`127.0.0.1:18084`，只回传字词时间戳。服务器把结果绑定到音频 SHA-256、原稿 SHA-256、暂存
素材 ID 和版本，全部成功后才执行 H3 安全切段并形成费用快照。生产云端不得直接调用本机
FunASR，也不得为此对外开放固定电脑的 18084 端口。

## 25. 动作参考视频自动片段池（2026-08-24）

用户每行仍只上传一条已经自行确认过内容的参考视频，页面不展示内部片段，不提供预览、排序、
禁用、手动指派或处理状态。数字人网站在费用 prepare 阶段执行固定策略：

1. 从 0 秒开始按 `0～3、3～6、6～9……` 切割；最后不足 3 秒的尾段完整保留；
2. 每段通过现有 FFmpeg 精确重编码为无音轨 MP4，原视频保持不变；
3. 使用版本化 `balanced_bag_v1`，每轮让所有片段各使用一次，并在候选多于一个时避免相邻音频
   分段使用同一动作片段；
4. 排列种子只包含原视频、完整音频、脚本摘要和算法版本，不包含时间或运行时随机值；
5. 每个 `H3SegmentConfig` 冻结动作片段索引、相对路径和 SHA-256。任务创建、失败重试、人工重
   生成及 soft-chain 下游激活都读取该快照，不重新分配；
6. 旧分段没有动作快照时回退到行级原始参考视频；切片失败发生在费用确认前，整次 prepare 回滚，
   不创建真实 RunningHub 任务，也不静默降级。

每个独立 H3 请求仍然只包含一个 `<Video 1>`，现有 Prompt 已将它限制为当前段的自然表演语言，
具体表情、姿态和手势可根据 `<Audio 1>` 自由适配；`loop_anchor` 继续由同一个 `<Picture 1>` 负责
所有分段的人物、穿搭、场景、构图以及首尾画面，因此动作池不需要增加 Prompt 变量或前端参数。

## 29. H3 远端 PNG 素材失效恢复（2026-08-31）

- 入口为人工重试后的正常上传链路；只识别最近一次明确的远端 `FAILED`、`LoadImage`、
  `FileNotFoundError` 和 `input/openapi/*.png`。不能据此断言平台内部的失效原因。
- 使用与失败远程任务绑定的上传回执匹配槽位和源文件 SHA-256；旧任务没有回执时仅允许
  `openapi/<源文件 SHA-256>.png` 精确匹配，不按节点编号猜测第一张图。
- `upload_recovery.py` 用标准库流式复制全部 PNG 数据块并校验 CRC，在 IEND 前增加不可见
  `tEXt` 标记。IDAT、颜色、透明度及其他原数据块保持原样，源文件和冻结输入完全不改。
  标记在同次逻辑重试内稳定，下一次远端失败后的人工重试使用新标记。
- `input_payload._h3_upload_receipt` 保存尝试/账号、槽位、文件指纹、大小、原文件名、远端
  相对文件名和上传时间；接受远程任务后绑定 ID，失败后归档到尝试历史。不记录 API Key、
  完整脚本、源文件绝对路径或带凭据 URL。重试清除当前错误不清除失败证据。

  在生成提交前停止。H3 远端失败不自动重提；下载重试、提交结果不明和成功分段保持原行为。
  重试入口以数据库状态及更新时间做条件更新，避免重复请求覆盖已入队或已接受的任务。
- 本次仅本地代码和模拟回归，无新依赖、无数据库迁移；生产更新与真实重试需另行确认。
