# H3 直达下载与全局 10 路队列实施方案

> 实施状态：本地功能主干已实现，相关自动化回归已通过；生产服务器、188/250 工作台和实际 Nginx 尚未部署。  
> 最后复核：2026-09-02。约 100 片真实 H3 联调、灰度观察和历史缓存清理仍需单独授权后执行。本文解决 H3 大文件交付与下载并发；豆包 Ark 请求并发另见《豆包请求全链路并发治理实施方案.md》。

## 1. 当前问题

1. 目前 JYD 在同步 H3 状态时，会在单次请求内临时创建下载线程池并等待下载完成。
2. 多个项目、多个页面或多次轮询可以各自创建线程池，实际并发数无法按整台工作台统一控制。
3. H3 视频经数字人服务器和 Nginx 转发时，会占用 Web 服务连接；Nginx 还可能把响应写入临时文件。
4. 大量片段同时下载时，登录、鉴权、状态查询等普通请求容易被拖慢，客户端可能在 15 秒超时后报连接失败。
5. 当前页面无法直观看到某个批次已经下载多少、当前速度及预计剩余时间。
6. 新旧 H3 交付方式并存，必须保证旧任务仍可下载，并避免旧结果覆盖新结果。

## 2. 目标与原则

- 每台 JYD 工作台机器全局最多同时下载 10 个 H3 片段；即使误开两个工作台进程，也不能扩大为 20 路。
- 10 是硬上限，不是必须跑满的固定值；实际活动数允许根据普通 API 延迟、下载错误率和磁盘压力在 2～10 路间自适应降低。
- 任意一个下载完成后立即补入下一个任务，不采用“每 10 个为一组，整组完成后再开始”的方式。
- 新 H3 结果由 JYD 直接从 RunningHub 下载，数字人服务器不接收、不落盘、不转发新 MP4。
- 数字人服务器仅保存任务号、结果 URL、结果签名及必要的状态元数据。
- Nginx 只保留旧链路兼容，并关闭该视频响应的缓冲。
- JYD 普通账号接口超时由 15 秒调整为 30 秒；媒体下载继续使用独立的长超时。
- 下载过程不得阻塞 H3 状态接口、登录、鉴权或其他页面操作。
- 页面只在每个批次的“片段检查”区域展示简短下载进度，不增加全局说明区。

## 3. 目标架构

```text
RunningHub
   │ 返回结果 URL、任务号、结果签名
   ▼
数字人服务器
   │ 仅保存和返回元数据，不下载 MP4
   ▼
JYD 状态同步
   │ 发现待下载片段并投递队列，立即返回
   ▼
工作台机器级下载管理器
   │ 机器级硬上限 10 路、连续补位、跨批次去重
   ▼
JYD 本地 .part 文件
   │ 校验通过且版本仍匹配
   ▼
原子替换为当前片段缓存
```

旧结果仍可走：`JYD -> 数字人服务器兼容视频接口 -> Nginx`。
该链路只用于兼容，不作为新 H3 任务的正常下载路径。

## 4. JYD 后端改动

### 4.1 新增机器级下载管理器

建议新增：

`src/jyd_probe/h3_segment_downloads.py`

职责如下：

- 在进程启动时只创建一个下载管理器。
- 使用最多 10 个持久工作线程，整个进程共享，不允许项目自行创建线程池。
- 启动时获取机器级单实例锁；同一数据目录已有活动下载器时，第二个进程不得再启动下载线程池，只能复用主实例或明确进入只读/不可下载状态。
- 活动下载数由自适应控制器限制在 2～10 路；任何配置和自适应逻辑都不得突破硬上限 10。
- 维护等待队列、运行集合、完成记录和批次进度快照。
- 下载结束后立即从队列取下一个任务，实现连续补位。
- 进程退出时停止接收新任务；保留身份和校验器仍有效、可继续续传的 `.part`，只清理已过期、损坏或身份不一致的残片。

建议提供以下接口：

- `enqueue(task)`：投递任务；重复任务直接返回现有状态。
- `get_batch_progress(batch_key)`：返回某批次聚合进度。
- `get_segment_state(download_key)`：返回单片段状态。
- `shutdown()`：停止调度并安全退出。

### 4.2 公平调度

- 全局活动下载数始终不超过 10。
- 等待任务按批次分组，以轮询方式从不同批次取任务。
- 一个包含大量片段的批次不能长期占满全部新增槽位。
- 同一批次内部按片段顺序稳定调度，便于用户先看到前部片段完成。

### 4.3 调整 H3 状态同步

修改 `src/jyd_probe/project_h3.py`：

- 移除 `sync()` 内部临时创建并等待 `ThreadPoolExecutor` 的逻辑。
- 状态同步只检查远端结果、本地缓存和版本信息。
- 对缺失且可下载的当前片段调用全局管理器 `enqueue()`。
- 投递后立即返回，不等待视频下载完成。
- 把对应批次的聚合下载进度加入本地 H3 状态响应。
- 本地已有且签名一致、校验通过的片段直接计为完成，不重复入队。

### 4.4 下载流程

每个下载任务按以下顺序执行：

1. 再次读取当前片段的结果签名。
2. 判断交付模式是 `runninghub_direct` 还是旧兼容模式。
3. 新模式直接请求 RunningHub 结果 URL，不携带数字人服务器鉴权信息。
4. 旧模式继续请求数字人服务器的受保护视频接口。
5. 流式写入同目录唯一 `.part` 文件，并持续更新字节数和速度。
6. 执行响应类型、文件大小、非空及媒体可读性校验。
7. 发布前再次确认片段当前结果签名没有变化。
8. 校验和版本均正确时，原子替换为当前本地缓存。
9. 短暂网络失败时保留可恢复的 `.part` 与配套元数据；确认版本过期、内容不一致、超限或媒体损坏时才删除。

下载失败只重试下载，不重新提交 H3 生成任务。重试采用有限次数、全随机抖动和服务端 `Retry-After`，并保留明确失败状态供后续轮询再次调度。

断点续传要求：

- 服务商响应支持 Range 时，保存 `ETag`、`Last-Modified`、已下载字节数和稳定结果身份。
- 重试使用 `Range` 与 `If-Range`；只有身份和校验器一致时才续传，否则从零开始。
- 服务器忽略 Range 并返回完整响应时必须截断旧 `.part`，不能把完整响应追加到残片后。
- 401/403 先刷新一次交付 URL，再以同一稳定结果身份续传；不得因此重新提交付费生成任务。

### 4.5 生命周期接入

修改 `src/jyd_probe/web_api.py` 或当前应用装配位置：

- 启动时创建唯一下载管理器，并注入所有 `ProjectH3Coordinator`。
- 所有账号、项目和浏览器页面共享同一实例。
- 应用关闭时调用 `shutdown()`。
- 页面关闭后，已经入队的任务继续下载，只要工作台进程仍在运行。

### 4.6 配置

新增或统一以下配置：

```text
JYD_H3_DOWNLOAD_WORKERS=10
JYD_H3_DOWNLOAD_MIN_WORKERS=2
JYD_H3_DOWNLOAD_ADAPTIVE_ENABLED=true
JYD_H3_DOWNLOAD_QUEUE_MAX=1000
JYD_H3_DOWNLOAD_VALIDATE_WORKERS=2
JYD_H3_DOWNLOAD_CONNECT_TIMEOUT_SECONDS=10
JYD_H3_DOWNLOAD_READ_IDLE_TIMEOUT_SECONDS=120
JYD_H3_DOWNLOAD_TOTAL_TIMEOUT_SECONDS=3600
JYD_H3_DOWNLOAD_MIN_FREE_GB=20
JYD_H3_DOWNLOAD_BATCH_MAX_GB=100
JYD_AUTH_TIMEOUT_SECONDS=30
```

要求：

- 下载并发默认值为 10，并设置合理上限，防止误配造成失控并发。
- 环境变量大于 10 时启动失败或钳制为 10，并记录明确配置错误；不得静默扩大并发。
- 等待队列必须有界；满载时保留远端完成状态，后续轮询再投递，不允许无限占用内存。
- 媒体校验使用独立的最多 2 路信号量，避免 10 个 ffprobe/解码校验同时打满磁盘与 CPU。
- 下载连接池与普通账号/API 连接池彻底分开；媒体连接不得占用登录、鉴权和状态查询的连接槽。
- 普通账号/API 请求默认超时改为 30 秒。
- H3 视频下载继续使用现有独立长超时，不能被改成 30 秒。
- H3 账号列表等已有专用长超时保持不变。
- 两台工作台使用相同配置，避免 188 与 250 行为不一致。

## 5. 状态、去重与版本安全

### 5.1 下载任务唯一键

下载键至少包含：

```text
owner_user_id
project_id
item_id
remote_batch_id
remote_item_id
segment_id
result_signature
```

相同键在等待、下载或已完成期间只能存在一份任务。

`result_signature` 必须是稳定结果身份，不能直接对带过期参数的下载 URL 求哈希。建议由以下字段组成：

```text
provider_task_id
output_node_id / output_index
media_type
provider_content_hash（如服务商提供）
```

下载 URL、URL 版本、过期时间和刷新时间单独保存为交付信息。URL 刷新但稳定结果身份不变时，不得重复下载或把正在下载的同一内容判成新版本。

### 5.2 状态定义

单片段内部状态建议为：

```text
queued / downloading / validating / ready / failed / stale
```

其中 `ready` 必须表示当前结果签名对应的文件已经校验并原子发布，而不是仅表示 HTTP 已下载完。

### 5.3 版本切换

- 用户重试或重新生成后，结果签名变化即视为新版本。
- 只有稳定结果身份变化才视为新版本；同一结果的签名 URL 刷新不算新版本。
- 旧版本正在下载时可以完成网络请求，但不得发布为当前文件。
- 检测到签名过期后，将任务标记为 `stale` 并删除临时文件。
- 新版本可独立入队，不受旧版本去重记录阻挡。
- 新版本可用前保留旧预览；界面应明确旧预览不是当前版本。

### 5.4 进程重启恢复

- 启动时读取 `.part` 配套元数据；稳定结果身份仍匹配且服务端支持续传的文件进入恢复队列，只有过期、不一致或超过保留期的残片才清理。
- 下次状态同步根据远端签名和本地元数据重新发现缺失任务。
- 不依赖内存中的“已完成”记录判断最终状态，本地文件和元数据才是恢复依据。

## 6. 下载进度协议

在 JYD 的每个 H3 批次状态中增加聚合字段，例如：

```json
{
  "download_progress": {
    "schema": "jyd.h3-download-progress.v1",
    "downloaded_count": 37,
    "total_count": 106,
    "bytes_per_second": 19500000,
    "estimated_remaining_seconds": 210
  }
}
```

统计口径：

- `downloaded_count`：当前结果签名已校验并发布到本地的片段数。
- `total_count`：该批次当前版本需要下载的片段总数。
- `bytes_per_second`：全部活动下载最近 5 至 10 秒的滚动总速度。
- `estimated_remaining_seconds`：优先按剩余字节和滚动速度计算。
- 无法获得文件总大小时，可结合最近完成片段平均大小估算。
- 数据不足或速度为零时返回空值，前端显示“剩余时间计算中”。

内部响应可以保留活动数、排队数和失败数用于诊断，但前端不展示这些额外文字。

## 7. 前端改动

修改 `apps/processor/frontend/new/index.html`：

- 复用现有 H3 状态轮询，不新增 WebSocket 或 SSE。
- 在每个批次对应的“片段检查”入口附近及弹窗标题区显示同一条进度。
- 不在页面顶部增加全局下载通知或说明面板。
- 前端只显示以下三项：

```text
已下载 37/106 · 18.6 MB/s · 剩余约 3 分钟
```

- 尚未获得速度时显示：`已下载 0/106 · 计算速度中 · 剩余时间计算中`。
- 全部完成后显示：`已下载 106/106 · 0 B/s · 已完成`。
- 进度变化必须加入前端渲染签名，避免状态已更新但界面不重绘。
- 单个视频预览仍以本地当前版本 `ready` 为准，不因批次其他片段未完成而阻塞。

## 8. 数字人服务器改动与配置

当前代码已有 `H3_DIRECT_DELIVERY_ENABLED` 和 `runninghub_direct` 交付契约，实施时以复用、验证和启用为主：

- 新 H3 成功结果只保存 RunningHub URL、任务号、结果签名和必要元数据。
- `normalized_video_path` 等服务器本地视频字段保持为空。
- 不新增 MP4 下载、临时缓存、对象存储或数据库二进制字段。
- 状态与元数据接口仍执行原有用户、设备和项目权限校验。
- RunningHub URL 必须继续通过协议和目标主机安全校验。
- URL 失效时，JYD 先刷新状态获取当前交付信息，再重试同一结果，不能自动重新生成。
- 软衔接可能保存的小型连续帧图片不属于视频存储，本次不改变。

## 9. Nginx 兼容链路

- 新 H3 直达下载不经过 Nginx，也不经过数字人服务器 Python 视频转发。
- 保留旧 `/api/workbench/h3-segments/{segment_id}/video` 接口。
- 对该兼容视频位置关闭响应缓冲：`proxy_buffering off;`。
- 同时设置 `proxy_max_temp_file_size 0;`，关闭该兼容路由的代理临时文件落盘，确认日志不再出现临时缓冲警告。
- 兼容接口仍需鉴权，不得直接暴露服务器历史文件目录。
- 不删除、不迁移历史 H3 视频文件。

## 11. 测试与验收

### 11.1 自动化测试

- 两个协调器、多个项目同时投递时，全进程活动下载数最大为 10。
- 第 11 个任务等待；任意活动任务结束后，下一个立即开始。
- 同一片段和结果签名被并发同步多次时只下载一次。
- 大批次与小批次同时存在时，小批次能获得下载槽位。
- 模拟下载阻塞时，H3 状态接口仍能快速返回。
- 直达模式只访问经过校验的 RunningHub URL，不携带数字人服务器令牌。
- 旧模式仍使用数字人服务器兼容接口并正常鉴权。
- 中断、空文件、超限、损坏媒体均不能覆盖当前有效缓存。
- 下载中签名变化时，旧结果被丢弃，新版本正常入队。
- 重启后能够保留合法续传残片、清理无效临时文件，并重新发现未完成片段。
- 进度数量、滚动速度和剩余时间按批次隔离。
- 前端只在片段检查区域展示下载数量、速度、剩余时间。
- 普通 API 超时为 30 秒，媒体下载和专用长请求超时未被误改。

### 11.2 联调验收

使用一个约 100 个片段的 H3 批次验收：

- JYD 同时建立的 H3 下载连接不超过 10 个。
- 下载完成后能立即补位，无整组等待空档。
- 打开多个项目或多个浏览器页面，并发上限仍为 10。
- 新结果的媒体流量从 JYD 直接到 RunningHub。
- 数字人服务器的新任务目录和持久化字段中没有 MP4。
- Nginx 不再承载新 H3 视频流，旧链路无响应缓冲临时文件警告。
- 下载期间登录、鉴权、状态查询可以正常使用，不再因 15 秒超时报连接失败。
- 每个批次的片段检查区域实时显示下载个数、当前速度和剩余时间。
- 重试单段后，旧下载不会覆盖新结果，其他片段不重复下载。

## 12. 发布顺序

1. 在本地完成 JYD 全局队列、进度、超时和前端改动及测试。
2. 验证数字人服务器现有直达契约，先保持直达开关关闭。
3. 更新 188 和 250 两台 JYD，使其都支持直达模式和全局 10 路队列。
4. 在旧兼容模式下验证两台机器的队列上限、进度显示和 30 秒普通超时。
5. 发布 Nginx 兼容路由的关闭响应缓冲配置并验证旧任务。
6. 在数字人服务器小范围开启 `H3_DIRECT_DELIVERY_ENABLED=true`。
7. 用新建 H3 任务确认 JYD 直达 RunningHub、服务器无 MP4 后再全面开启。
8. 持续观察 JYD 下载错误、队列长度、登录/鉴权延迟、Nginx 临时文件和服务器磁盘。

## 13. 回滚方案

- 关闭 `H3_DIRECT_DELIVERY_ENABLED`，后续新任务恢复旧交付模式。
- 将 `JYD_H3_DOWNLOAD_WORKERS` 临时调低后重启工作台，可降低局域网或磁盘压力。
- 保留旧视频接口和旧缓存读取逻辑，不删除现有文件与元数据。
- 前端进度字段不存在时按旧状态渲染，保证服务器和 JYD 可分步回滚。
- 已经产生的直达结果在服务器上没有 MP4；回滚期间必须保留支持直达的 JYD，直到这些批次下载完成。
- 不通过关闭开关强行重建已完成 H3，也不自动产生新的计费任务。

## 15. 实施前基线与必须补齐的工程约束

### 15.1 2026-09-02 基线

实施时不得把“代码里已有入口”误判为“生产已经启用”：

- 实施前数字人服务器已有 `H3_DIRECT_DELIVERY_ENABLED` 和 `runninghub_direct` 契约，但复核时生产开关未设置，默认仍为关闭。
- 实施前 JYD 同步会在单次同步中临时创建线程池，默认并发 3、上限 8，并等待本次下载结束；本地代码现已替换为机器级统一 10 路队列。
- 复核时生产 Nginx 的 H3 兼容路由尚未同时落实 `proxy_buffering off` 与 `proxy_max_temp_file_size 0`；本地模板已补齐，但生产仍未发布。
- 因此发布必须同时包含“服务端契约复核、JYD 下载器、Nginx 兼容配置、灰度开关”四部分，不能只改其中一处。

### 15.2 媒体连接与普通 API 隔离

- H3 下载器使用独立、持久的 HTTP 连接池，最大连接数与机器级活动下载上限相同，并启用连接池满时阻塞。
- 登录、鉴权、状态同步和交付 URL 刷新使用另一套高优先级连接池，不与媒体流共享连接槽。
- 下载超时拆为连接超时、连续无数据超时和总时限，禁止用一个长 read timeout 代替全部边界。
- 可选增加整机总带宽上限。若不配置带宽上限，也必须通过自适应并发保护普通 API。
- 同一目标主机连续出现连接错误、超时或 5xx 时进入短时熔断；半开阶段只允许一个探测下载，避免 10 路一起重试。

### 15.3 下载 URL 安全

数字人服务器和 JYD 必须执行相同安全边界：

- 只允许 HTTPS、无用户名密码、受控端口，并使用 RunningHub/COS 的精确主机白名单；不能只判断“看起来像 HTTPS”。
- DNS 解析后拒绝 loopback、私网、链路本地、保留地址和云元数据地址。
- 默认关闭自动重定向；如业务必须跟随重定向，每一跳都重新执行协议、主机、端口和解析地址校验，并限制跳数。
- 直达 RunningHub 时不得转发数字人服务器的 Authorization、设备令牌、Cookie 或其他内部鉴权头。
- 日志只记录主机、稳定结果身份、状态码、字节数和内部请求 ID，不记录完整签名 URL。

### 15.4 错误分类、刷新、重试与熔断

| 场景 | 处理 |
| --- | --- |
| DNS、连接失败、连接超时、读空闲超时 | 有限重试；全随机抖动；允许断点续传 |
| 429、502、503、504 | 遵循 `Retry-After`，否则指数退避加全随机抖动 |
| 401、403 | 只刷新一次交付 URL；稳定结果身份不变时继续同一下载 |
| 404 | 先刷新交付信息；仍为 404 才记为无效结果，不自动重做 H3 |
| 其他 4xx | 不盲目重试，记录稳定错误码 |
| 内容长度、媒体校验或校验和失败 | 从零重下，次数严格受限；重复失败进入人工可见失败状态 |
| 稳定结果身份已变化 | 当前任务标为 `stale`，不得发布；新版本单独入队 |

所有退避都必须带随机抖动，不能让 10 个任务在同一秒整齐重试。熔断按目标主机统计，不影响登录/鉴权连接池。

### 15.5 原子发布和崩溃一致性

不能采用“先覆盖 MP4，再覆盖元数据”的两步发布。建议本地缓存结构为：

```text
segment-cache/
  versions/
    {result_signature}/
      video.mp4
      metadata.json
  current.json
```

- 下载和校验均在版本目录内完成，版本目录写完后再原子替换 `current.json`。
- 预览和后续处理只读取 `current.json` 指向的完整版本，不能分别猜测视频和元数据。
- 新版本发布前保留旧版本；发布成功后只有在保留策略另行授权时才清理过旧版本。
- 崩溃后若版本目录完整但指针未切换，不自动把孤立文件发布为当前版本；下次同步按远端稳定身份重新校验/下载。目录不完整时进入合法续传，身份不一致或损坏时才清理。
- 进度和完成状态从版本目录及 `current.json` 恢复，内存状态只用于加速。

### 15.6 磁盘、文件和关闭边界

- 投递前和写入过程中检查剩余磁盘空间；低于阈值时暂停新下载并返回 `DISK_SPACE_LOW`，不得把磁盘写满。
- 对单文件大小、批次累计大小、响应 Content-Length 和实际写入字节设置上限。
- 应用关闭时停止接收新任务、取消等待任务、给活动任务短暂落盘元数据时间，然后退出；不得无限等待。
- 启动时先统计超过保留期的残片、孤立版本和旧完成记录；默认不自动删除。只有明确配置保留策略并经用户授权后才执行清理，正在续传且身份有效的残片不得误删。
- 下载任务和媒体校验任务都要有 watchdog，防止线程永久卡住导致队列不再补位。

## 16. 观测、自适应和告警

至少记录以下无敏感信息指标：

- 机器级活动数、有效并发上限、各批次等待数、队列总深度、最老等待时间。
- 直达与兼容链路的请求数、下载字节、成功率、重试数、URL 刷新数和熔断状态。
- 连接耗时、首字节耗时、下载速度、校验耗时、总耗时及错误码分布。
- 普通登录/鉴权/状态接口的 p50、p95、p99 延迟和错误率。
- 磁盘剩余空间、残片数量/字节、孤立版本数量和清理结果。

自适应默认策略可先按以下值实现，并在本地压测后校准：

1. 初始有效并发为 2，稳定后逐步升到 10，每分钟最多增加 1。
2. 普通 API p95 连续 3 个窗口超过 2 秒、普通 API 错误率超过 2%、目标主机熔断或磁盘繁忙时，每次至少降低 1。
3. 普通 API p95 持续 5 分钟低于 1 秒、下载错误率低且磁盘正常时，才允许逐步恢复。
4. 无论指标如何，有效并发不得小于 2 或大于 10；紧急磁盘不足时允许暂停为 0。

告警不得只看下载失败，还要覆盖普通 API 延迟、队列最老等待时间、磁盘不足、残片持续增长和兼容链路流量异常上升。

门禁：新任务视频流量不经过数字人服务器，旧任务仍可下载，普通 API 指标不劣化。

### 阶段 E：全面开启与清理策略

- 全面开启后继续保留旧兼容接口，不立即迁移或删除历史文件。
- 稳定观察至少一个完整业务周期后，再单独评审历史缓存清理；清理不属于本文默认授权。

## 18. 补充验收矩阵

除第 11 节外，必须增加：

- 同时启动两个工作台进程，整台机器的 H3 活动下载总数仍不超过 10。
- 下载中签名 URL 到期并刷新，但稳定结果身份不变时继续同一任务且不重复发布。
- 下载到 60% 后断网并重启工作台，恢复后从合法偏移续传；服务商不支持 Range 时安全从零开始。
- 302 跳转到私网、云元数据地址、非白名单域名或异常端口时被拒绝。
- 磁盘低于阈值时暂停新下载，旧预览和普通 API 仍可用，恢复空间后可继续。
- 在写完新视频、尚未切换 `current.json` 时强制终止进程，重启后不会出现新视频配旧元数据。
- 10 路慢下载持续运行时，登录、鉴权和 H3 状态查询达到发布前设定的 p95 门槛。
- 兼容路由确认 `proxy_buffering off` 和 `proxy_max_temp_file_size 0` 均生效。

## 19. 与豆包请求治理的边界

本方案只能解决 H3 视频大流量占用连接、磁盘和同步线程的问题，不能解决内容分析一次启动多批请求造成的豆包 Ark 排队、重试叠加和 600 秒总超时问题。后者必须按《豆包请求全链路并发治理实施方案.md》单独实施；两套管理器、连接池、超时和指标不得共用，但普通 API 延迟可作为两边共同的保护信号。
