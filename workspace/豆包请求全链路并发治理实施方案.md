# 豆包请求全链路并发治理实施方案

> 文档状态：本地功能主干已实施，生产迁移、2→5→10 灰度、188/250 更新和真实付费冒烟待单独授权  
> 编写日期：2026-09-02；本地实施复核：2026-09-03  
> 适用范围：JYD 剪映工作台、数字人服务器、豆包 Ark 内容分析与语义视觉请求  
> 安全边界：本文只给出实施方案；未经单独授权，不调用真实付费接口、不部署生产、不修改云端账号数据库。

## 1. 要解决的问题

当前系统在单个批次内已经做了并发控制，但还没有形成从“多个工作台批次”到“数字人服务器”再到“豆包 Ark”的统一请求预算。

按 2026-09-02 代码与生产配置复核：

- JYD 单个内容分析批次最多并发 10 行。
- JYD 后台批次调度器最多同时运行 4 个批次，因此理论上可同时向数字人服务器发出 40 个内容分析 HTTP 请求。
- JYD 单个请求总等待时间为 600 秒。
- 数字人服务器用进程内 `ArkConcurrencyLimiter` 将 Ark 活动请求限制为 10，内容分析和语义视觉共用该限制。
- 服务器队列默认最多等待 300 秒；当前生产是单 Uvicorn 进程，所以进程内上限暂时等同于整台服务器上限。
- 当前内容分析路由是同步处理；等待信号量的请求仍可能占用 FastAPI 通用工作线程。
- Ark 客户端按请求新建 `requests.Session`，跨请求连接复用不足。
- 规划阶段仍按账号配置执行有限重试；字幕专用阶段固定单次，失败后走本地确定性降级。
- 当前生产启用账号的请求超时为 120 秒、额外重试为 2，即规划阶段最多可能尝试 3 次。

最不利时间预算可能达到：

```text
服务器排队 300 秒
+ 规划请求 120 秒 × 3 次
+ 字幕请求 120 秒 × 1 次
+ 重试退避与网络开销
> 780 秒
```

该路径已经超过 JYD 的 600 秒等待上限。结果可能是工作台先报告网络失败，而服务器仍在排队、调用或重试；用户再次点击后又形成重复请求和重试风暴。

保留日志中连接错误和超时数量目前不高，只能说明已保存样本没有大面积报错，不能证明 40 路突发、长排队和重试叠加已经安全。

## 2. 目标与非目标

### 2.1 目标

- 每台 JYD 工作台所有项目和所有后台批次合计，最多同时向数字人服务器发送 10 个豆包分析请求。
- 数字人服务器所有内容分析、语义视觉及后续接入同一 Ark 资源池的业务，合计最多同时执行 10 个真实 Ark 请求。
- 超过 10 路的任务进入有界公平队列，不占用通用 Web 工作线程，不无限堆积。
- 整条链路有统一总时限，服务器必须早于 JYD 超时结束并返回明确结果。
- 网络重试不产生第二份付费调用；同账号、同契约、同脚本的并发重复请求合并为同一个进行中任务。
- Ark HTTP 连接可复用，连接、读取、总时限分离，重试带随机抖动和熔断。
- 内容分析失败继续沿用现有本地字幕/BGM 安全降级，不影响 MiniMax、RunningHub、剪映生成和已有结果。
- 全程不在日志、指标或幂等记录中保存 API Key、完整脚本或豆包完整原始响应。

### 2.2 非目标

- 不修改内容分析 Prompt、公开 JSON 契约、字幕断点语义或音乐 Top1 规则。
- 不把内容分析失败改成重新生成声音、视频或剪映工程。
- 不用提高 Uvicorn worker 数绕过并发问题。
- 不把 H3 视频下载接入本请求池；H3 大文件流量由《H3直达下载与全局10路队列实施方案.md》治理。

## 3. 目标架构

```text
多个项目 / 多个页面 / 多个后台批次
        │
        ▼
JYD 全局 ContentAnalysisRequestManager
机器内最多 10 路、有界公平队列、同请求合并、统一 600 秒预算
        │
        ▼
数字人服务器鉴权、缓存和幂等账本
        │
        ▼
ArkRequestManager 专用队列与专用执行器
服务器全局最多 10 路、内容分析与语义视觉共享、总预算 540 秒
        │
        ▼
线程内持久 Session / 独立连接池
        │
        ▼
豆包 Ark
```

通用登录、鉴权、状态查询不进入 Ark 专用队列。Ark 排队也不得占住通用 FastAPI 线程池。

## 4. JYD 工作台实施

### 4.1 新增全局请求管理器

建议新增：

`src/jyd_probe/content_analysis_requests.py`

职责：

- 应用启动时创建唯一实例，所有 `ProjectContentAnalysisCoordinator` 共享。
- 最多 10 个活动 HTTP 请求；后台批次调度器的 4 路只表示可同时推进 4 个批次，不能再各自拥有 10 路请求池。
- 等待队列按项目/批次轮询，避免一个大项目长期占满新增槽位。
- 队列必须有界；满载时任务保留为可重试的待分析状态，不无限增加线程和内存。
- 同一逻辑请求在等待、运行或短期结果保留期间只存在一份。
- 应用退出时停止接收新任务、保存必要状态，并在有限时间内结束。

建议接口：

- `submit(request)`：提交或合并逻辑请求。
- `get_batch_progress(batch_key)`：返回完成、活动、等待、失败数量。
- `cancel_stale(item_key, script_hash)`：脚本变化后取消尚未发出的旧请求。
- `shutdown()`：有限时关闭。

### 4.2 请求身份与客户端重试

每次用户触发分析时生成稳定的 `analysis_operation_id`，同一次操作的网络重试必须复用该 ID。请求身份至少包含：

```text
owner_user_id
project_id
item_id
script_sha256
contract_version
prompt_version
force_refresh_generation
analysis_operation_id
```

- 普通重复点击、页面重复轮询和客户端网络重试复用原操作 ID。
- 用户明确执行新的“强制刷新”时才生成新的 `force_refresh_generation` 和操作 ID。
- 请求已经收到服务器明确业务响应后，JYD 不在 HTTP 层自行重做付费分析。
- 连接建立失败、服务器明确表示尚未准入 Ark、或收到带 `Retry-After` 的队列满响应时，才允许在总预算内重试。

### 4.3 JYD 默认配置

```text
JYD_CONTENT_ANALYSIS_MAX_IN_FLIGHT=10
JYD_CONTENT_ANALYSIS_QUEUE_MAX=1000
JYD_CONTENT_ANALYSIS_TOTAL_TIMEOUT_SECONDS=600
JYD_CONTENT_ANALYSIS_CONNECT_TIMEOUT_SECONDS=10
JYD_CONTENT_ANALYSIS_RETRY_MAX=2
```

`MAX_IN_FLIGHT` 大于 10 时启动失败或钳制为 10，并记录配置错误。两台工作台必须使用相同默认值。

## 5. 数字人服务器实施

### 5.1 专用 Ark 请求管理器

建议新增：

`runninghub_mvp/app/services/ark_request_manager.py`

要求：

- 内容分析和语义视觉统一提交到一个专用管理器，真实 Ark 活动调用硬上限为 10。
- 业务采用公平队列；可按“内容分析、语义视觉”轮询，禁止单一业务长期占满新增槽位。
- 队列有界，建议默认 200；队列满时立即返回结构化 429 和 `Retry-After`，不继续占用服务器资源。
- 路由改为异步等待专用 Future，或将阻塞 Ark 调用放入独立 `ThreadPoolExecutor(max_workers=10)`；不得使用 FastAPI 通用线程池承载长时间排队。
- 鉴权、缓存查询和请求校验在准入前完成；真实 Ark 槽位只包围实际第三方调用，不把本地解析、数据库保存和响应序列化计入活动调用数。
- 字幕专用调用如属于同一个分析操作，继续占用同一全链路总预算，但只在真正访问 Ark 时占一个槽位。

当前生产只有一个 Web 进程，可以先使用进程内管理器。若以后启用多个 Web worker，必须先切换 Redis 信号量/租约或数据库租约；在 `ARK_LIMITER_SCOPE=process` 时检测到多 worker 应拒绝启动或给出强告警，不能让 4 个进程各跑 10 路。

### 5.2 幂等账本与进行中请求合并

现有脚本缓存继续作为“已完成结果”的第一道保护；另外增加轻量请求账本，建议表名：

`content_analysis_requests`

只保存：

- `analysis_operation_id`、内部用户 ID、脚本哈希、模型/契约/Prompt 版本。
- `QUEUED / RUNNING / SUCCEEDED / PARTIAL / FAILED / EXPIRED` 状态。
- 分支状态、稳定错误码、创建/开始/结束/过期时间。
- 已完成结果关联到现有内容分析缓存，不复制完整脚本或完整模型响应。

处理规则：

1. 相同操作 ID 已完成：直接返回已保存结果。
2. 相同业务键正在运行：后来的请求加入同一 Future，不再占用第二个队列位置或 Ark 槽位。
3. Ark 已成功但客户端断线：服务器先提交缓存和账本，再结束响应；客户端重试能读取结果。
4. 服务重启后：对长期 `RUNNING` 记录标为可诊断的 `EXPIRED`；如现有缓存已落盘则返回缓存，不自动再次付费。
5. 账本按保留期清理，只保留哈希和诊断信息。

新增数据库迁移属于实施阶段的显式步骤，必须先备份并按项目迁移规范执行；本文不授权立即修改生产数据库。

## 6. 统一时限预算

建议首版默认值：

```text
JYD 总等待预算                         600 秒
服务器分析总预算                      540 秒
服务器排队预算                        120 秒
Ark 连接超时                           10 秒
规划阶段单次读取上限                  120 秒
规划阶段总尝试次数                      2 次（最多重试 1 次）
字幕专用阶段总尝试次数                  1 次
重试退避总预留                         30 秒
服务器返回与网络余量                   60 秒
```

在 120 秒账号超时下，最坏预算为：

```text
排队 120 + 规划 120 × 2 + 字幕 120 + 退避 30 = 510 秒
```

该值小于服务器 540 秒和 JYD 600 秒，仍留有返回余量。

实施规则：

- JYD 通过 `X-JYD-Request-Budget-Ms` 发送相对预算，服务器取“客户端剩余预算、服务器最大预算、账号策略”中的最小值，避免机器时钟差。
- 每个阶段开始前计算剩余预算；阶段单次 timeout 必须钳制到剩余时间，不能在总时限快结束时再启动一个 120 秒请求。
- 账号的 `timeout_seconds` 和 `max_retries` 保留为策略上限，但有效尝试次数和单次时限必须再受全链路预算限制。
- 服务器到达总时限后返回 `ARK_TOTAL_DEADLINE_EXCEEDED`，取消尚未开始的任务；已开始的阻塞调用必须由底层 read timeout 保证可退出。
- 老版本 JYD 不发送预算头时，服务器使用 540 秒默认值，保持向后兼容。

## 7. HTTP 连接池

不在线程间无保护地共享一个可变 `requests.Session`。首版采用“专用执行器每个工作线程一个 Session”：

- Session 按 Ark Base URL 和安全配置指纹创建，使用 `HTTPAdapter`，连接池大小为 10，`pool_block=true`。
- 连接池只服务 Ark，不与 RunningHub、H3 下载或普通数字人 API 共用。
- API Key 通过单次请求头注入，不写入可跨账号复用的全局默认头。
- 配置或 Key 轮换后淘汰旧指纹 Session；应用关闭时显式关闭全部 Session。
- timeout 使用 `(connect_timeout, read_timeout)`，并由第 6 节总预算再次钳制。
- 禁止把请求体、Authorization 或完整服务商响应写入调试日志。

如后续迁移为 `httpx.AsyncClient`，必须保持同样的连接上限、账号隔离、总时限和日志边界，不能只替换库名。

## 8. 重试、退避与熔断

### 8.1 可重试

- DNS/连接异常、连接超时、读取超时。
- HTTP 429、502、503、504。
- 服务商明确标记为临时性的错误。

### 8.2 不重试

- API Key、权限、配额策略等普通 4xx。
- 请求 JSON、响应 JSON、Schema 或业务字段校验失败。
- 字幕专用请求失败后的本地确定性降级。
- 总预算不足以安全完成下一次尝试。

### 8.3 退避

- 优先遵循合法的 `Retry-After`，但不得超过剩余总预算。
- 否则使用指数退避加 full jitter，禁止固定 1、2、4 秒让并发请求同时再次打到 Ark。
- 日志记录阶段、尝试次数、等待毫秒、服务商 request ID 和稳定错误码，不记录脚本及 Key。

### 8.4 熔断

- 按 Ark Base URL、模型和账号配置指纹统计连续临时失败。
- 达到阈值后短时打开熔断器，新任务停留在有界队列或快速返回可重试错误。
- 冷却后只允许一个半开探测请求；成功再逐步恢复。
- 鉴权失败不做半开探测风暴，应直接返回配置错误等待管理员处理。

## 9. API 状态与错误协议

建议补充稳定错误码：

| HTTP | 错误码 | 含义 | JYD 行为 |
| --- | --- | --- | --- |
| 429 | `ARK_QUEUE_FULL` | 尚未准入，服务器队列已满 | 遵循 `Retry-After`，复用操作 ID |
| 503 | `ARK_CIRCUIT_OPEN` | 豆包临时熔断 | 延后重试，不新建付费操作 |
| 504 | `ARK_QUEUE_WAIT_TIMEOUT` | 排队预算耗尽 | 当前行安全降级或由用户显式重试 |
| 504 | `ARK_TOTAL_DEADLINE_EXCEEDED` | 全链路预算耗尽 | 不自动连环重试 |
| 502 | `ARK_UPSTREAM_TRANSIENT` | 上游临时错误且重试已耗尽 | 保存失败状态并安全降级 |
| 422 | `ARK_RESPONSE_INVALID` | 响应契约不合法 | 不传输重试，保留合法分支 |

响应附带内部 `request_id`、`analysis_operation_id`、是否已准入、是否来自缓存、尝试次数和各阶段耗时。任何字段都不能包含完整脚本或密钥。

## 10. 观测与告警

至少增加：

- JYD：活动请求数、有效上限、等待数、最老等待时间、各批次完成/失败数。
- 服务器：Ark 队列深度、活动数、队列等待 p95/p99、各阶段耗时、总耗时。
- 缓存命中数、进行中请求合并数、操作 ID 重放数和避免的重复调用数。
- 连接复用率、连接建立耗时、429/5xx/timeout 次数、重试次数、`Retry-After` 等待和熔断状态。
- 内容分析与语义视觉各自的准入数、成功/部分成功/降级/失败数。
- 登录、鉴权、H3 状态等普通接口 p95/p99 和错误率，验证 Ark 排队没有拖慢通用服务。

建议告警：

- Ark 队列最老等待超过 60 秒。
- 队列深度连续 5 分钟超过容量 70%。
- 普通 API p95 连续 3 个窗口超过发布前基线两倍。
- 同一账号连续鉴权失败、熔断持续超过 5 分钟或总时限错误持续出现。
- 同一操作 ID 对应多个真实 Ark 调用，视为幂等缺陷。

## 12. 分阶段实施计划

### 阶段 0：基线与假服务

- 固定当前多批次理论 40 路、服务器 10 路排队和 600/780 秒预算冲突的回归测试。
- 建立本地 Ark 假服务，模拟慢响应、断流、429、5xx、非法 JSON、响应丢失和 `Retry-After`。
- 所有测试使用 mock，不调用真实付费接口。

完成门禁：能稳定复现超时倒挂、通用线程池占用和同步重试问题。

### 阶段 1：服务器总预算与专用队列

- 先保持现有公开响应契约，新增专用管理器、有界队列、总预算和指标。
- 内容分析与语义视觉共享服务器硬上限 10。
- 将排队从通用 FastAPI 线程池移出。

完成门禁：100 个并发模拟请求下真实上游活动数不超过 10，登录/健康检查仍快速响应。

### 阶段 2：连接池、重试与幂等

- 接入线程内 Session、连接复用、full jitter、`Retry-After` 和熔断。
- 增加操作 ID、进行中合并和请求账本迁移。
- 验证响应丢失后重试不会产生第二次上游调用。

完成门禁：相同业务键及相同操作 ID 的并发/重放均只计一次真实 Ark 调用。

### 阶段 3：JYD 全局 10 路

- 用全局请求管理器替换“每批次各 10 路”。
- 保留 4 个批次可推进，但所有批次共享 10 个 HTTP 槽位。
- 增加公平调度、状态恢复、操作 ID 和预算头。

完成门禁：4 个批次各 25 行同时运行时，单台 JYD 到服务器的活动请求总数始终不超过 10，小批次不会饿死。

### 阶段 4：本地联调和灰度

- 先以服务器上限 2 灰度，再按 5、10 逐级增加。
- 服务器先发布向后兼容版本，再更新 188/250 工作台包。
- 工作台全部更新后再启用依赖新操作 ID 的严格策略。
- 真实 Ark 冒烟需用户单独授权，使用最小样本并确认计费。

完成门禁：无 600 秒客户端先超时、无重复计费调用、普通 API 指标不劣化。

## 13. 自动化测试与验收

必须覆盖：

- 4 个 JYD 后台批次并行时，本机 HTTP 活动请求合计不超过 10。
- 两台 JYD 同时请求时，服务器真实 Ark 活动数合计不超过 10。
- 第 11 个服务器任务进入队列，任意活动任务结束后立即补位。
- 大批次与小批次并存时，小批次能持续获得槽位。
- 100 个任务长时间排队时，登录、鉴权、健康检查和状态接口仍满足延迟门槛。
- 同脚本并发请求、重复点击、网络重试和响应丢失只产生一次真实上游调用。
- 规划请求最多 2 次，字幕请求最多 1 次；Schema 错误不重试。
- 429 使用 `Retry-After`，其他临时错误使用带随机抖动的退避。
- 总预算不足时不再启动下一阶段；服务器总能早于 JYD 600 秒结束。
- 配置或 Key 轮换后旧 Session 被淘汰，账号之间不会串用 Authorization。
- 服务重启后能从缓存/账本识别已完成操作，陈旧 RUNNING 不会自动重复付费。
- 多 Uvicorn worker 且仍使用进程级限制时启动检查失败或明确阻止上线。
- 内容分析失败仍保持当前字幕/BGM 本地降级，不影响已有音频、视频和剪映流程。
- 日志与指标不出现 API Key、完整脚本、完整请求体或完整豆包响应。

发布验收建议以“2 台工作台、4 个批次、每批 25 行”的 100 行场景执行，并记录：

- JYD 峰值、服务器峰值、队列等待 p95/p99、总耗时 p95/p99。
- 真实 Ark 请求数与逻辑任务数、缓存命中数、合并数和重试数。
- 普通 API 发布前后延迟和错误率。
- 每行最终分支状态以及是否使用本地降级。

## 14. 发布、回滚与数据迁移

发布顺序固定为：

1. 备份数据库并发布向后兼容的服务器代码及迁移。
2. 保持新并发管理器开关关闭，完成迁移头、健康检查和旧客户端回归。
3. 打开服务器专用队列，先限制 2 路观察，再升到 5 路。
4. 更新两台 JYD 安装包，使所有批次共享全局 10 路并发送操作 ID。
5. 服务器升到 10 路，完成 100 行验收后全面启用。

建议灰度开关：

```text
ARK_REQUEST_MANAGER_ENABLED=false
ARK_MAX_CONCURRENCY=10
ARK_QUEUE_MAX=200
ARK_ANALYSIS_TOTAL_TIMEOUT_SECONDS=540
ARK_QUEUE_WAIT_TIMEOUT_SECONDS=120
ARK_CONNECT_TIMEOUT_SECONDS=10
ARK_PLANNING_MAX_ATTEMPTS=2
ARK_CIRCUIT_BREAKER_ENABLED=true
```

回滚：

- 先把服务器并发临时降为 2，不删除缓存和请求账本。
- 关闭 `ARK_REQUEST_MANAGER_ENABLED` 回到旧限制器时，必须同时保持单 Web 进程，避免扩大为多进程各 10 路。
- 新字段对旧 JYD 可选，旧客户端仍能使用默认 540 秒预算。
- 数据库迁移只新增表/索引，不删除旧字段；代码回滚时保留新表，不做破坏性降级迁移。
- JYD 新管理器出现问题时可回滚安装包，但服务器硬上限和总预算继续兜底。

## 15. 完成定义

只有同时满足以下条件才算完成：

- JYD 不再出现“4 个批次 × 每批 10 路”的 40 路请求放大。
- 数字人服务器在当前和未来多进程部署方式下，都有明确且经过测试的全局 10 路边界。
- 服务器最长处理预算严格小于 JYD 等待预算，不再存在 780 秒对 600 秒的倒挂。
- 排队不占用通用 Web 线程，Ark 慢请求不拖垮登录、鉴权和状态查询。
- 同一逻辑操作在重复点击、断线重试和响应丢失场景下不会重复调用 Ark。
- 连接复用、随机退避、熔断、指标、告警、灰度和回滚均有自动化测试与实际验收记录。

### 16.1 实施时的固定顺序

1. 先做服务器专用队列和总预算，让旧工作台请求也受到保护。
2. 再做幂等账本与连接层，解决重复付费和重试风暴。
3. 服务器保持向后兼容后，再更新 JYD，把每批次独立 10 路收口为整机 10 路。
4. 最后才执行数据库生产迁移、两台工作台更新和真实付费冒烟；这些均不由本文自动授权。

### 16.2 与当前 H3 改动的关系

- 可复用的是工程方法：有界公平队列、硬上限、独立连接池、总预算、熔断、健康诊断和灰度门禁。
- 不复用实例或连接池：豆包是短/长混合 JSON 付费请求，H3 是大文件流式下载，两者必须各自限流和统计。
- H3 本地实现完成后，只能减少视频流量对网络和普通 API 的干扰，不能把当前潜在的 `4 × 10 = 40` 路豆包请求自动降为 10；`JYD-ARK-01` 仍是必做项。
