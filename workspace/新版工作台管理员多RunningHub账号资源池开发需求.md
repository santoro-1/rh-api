### 2026-08-12 双账号池与兼容开关调整决策（当前最高优先级）

> 本节是当前实施依据。它只在新双池分支中覆盖 2026-08-11 的同账号绑定决策；步骤 1～8 的
> 完成记录仍是准确的历史记录。开关关闭时，2026-08-11 的同账号规则和当前代码行为保持不变。

#### 1. 保留当前流程，使用开关选择分支

- 不停用当前 RunningHub 账号，也不取消它现有的 SeedVR2 能力。工作时间测试仍可继续使用
  当前已完成的“同一账号顺序执行数字人和 SeedVR2”流程。
- 新增云端全局功能开关，建议命名为 `RUNNINGHUB_DUAL_POOL_ENABLED`，默认关闭。不得由前端
  请求体直接传入一个布尔值来绕过云端控制。
- 同时新增用户级双池授权。只有“全局开关开启 + 当前登录用户拥有双池授权 +
  `source_channel=new_workbench` + 工作流为 `digital_human`”时，才进入 `dual_pool_v1`；其余
  情况全部进入当前 `same_account_v1`。
- 第一位受控测试用户为 `Cx_ceshi`。实现时应先通过用户名定位其不可变网站用户 ID，再保存
  用户级授权；业务代码不得长期硬编码或每次用字符串比较 `Cx_ceshi`。该授权是本需求对原
  “仅 `is_admin=true`”规则的明确测试例外，不自动给其他普通用户开放资源池。
- 每个项目级/批次级 4A 操作必须保存不可变执行模式快照 `same_account_v1` 或
  `dual_pool_v1`。开关或授权后来改变，不得迁移、换号或重提已经启动的付费任务：关闭时启动
  的任务按同账号分支完成，开启时启动的任务按双池分支完成。

| 全局开关 | 当前用户具有双池授权 | 新版工作台执行模式 |
| --- | --- | --- |
| 关闭 | 任意 | `same_account_v1`，完整保留当前流程和接口兼容行为 |
| 开启 | 否 | `same_account_v1` |
| 开启 | 是 | `dual_pool_v1`，使用数字人池与 SeedVR2 池 |

#### 2. 双池分支的职责边界

- 当前已经实现的 `runninghub_execution_accounts` 资源池在双池分支中专门承担数字人生成。
- 新增一个彼此独立的普通 RunningHub 执行账号池，专门承担 SeedVR2 放大；账号拥有独立的
  API Key、Base URL、SeedVR2 AI App ID、最大并发、启用状态、备注、健康/冷却状态和凭据
  指纹。
- 数字人阶段成功并把源视频下载、校验并持久化后，释放数字人执行账号的槽位；随后 SeedVR2
  调度器从本次 SeedVR2 账号快照中独立选择并原子预留账号。两个池各自按真实 API Key 计算
  并发，当前每个真实账号最多并发 5。
- 同一个真实 API Key 在数字人池内部、SeedVR2 池内部或两个池之间都不得重复形成容量；云端
  必须使用相同的不可逆指纹做跨池判重和活动容量合并。
- 双池逻辑优先新增独立的配置、调度和 Worker 服务，由一个很薄的服务端分支选择入口调用；
  现有 `same_account_v1` 主流程保持语义不变。共享的 RunningHub 客户端、加密、日志和尝试
  原语可以安全复用，不要求复制凭据处理代码。

#### 3. SeedVR2 重试与换号边界

- SeedVR2 普通工作流失败默认在原 SeedVR2 执行账号上重试，复用已经保存的数字人源视频，
  不重新生成数字人，也不因为一次任务失败就换账号。
- 只有确认“该账号不可用于新的 SeedVR2 付费尝试”时，新尝试才允许在本次不可变 SeedVR2
  账号快照内换到其他健康账号。确认账号不可用至少包括：凭据无效或被撤销、SeedVR2 工作流
  无权限或不可访问、账号被全局停用而禁止新尝试，或达到明确阈值的账号级健康探测失败并进入

### 2026-08-11 两阶段账号绑定补充决策（历史基线，仅适用于 `same_account_v1`）

- 当前数字人每个分段在源视频成功后还会执行一次 SeedVR2 清晰化。产品上将这两个远程
  任务视为同一个视频分段的两阶段执行流水线，不允许分别调度到不同 RunningHub 账号。
- 某个 `GenerationTask` 首次分配给执行账号 B 后，该分段的数字人生成、对应 SeedVR2、
  状态查询、取消、下载和恢复都必须使用 B；分配给账号 C 的分段同理。
- 账号槽位从数字人上传前原子预留，一直保留到 SeedVR2 清晰结果下载完成、最终失败或安全
  取消后才释放。最大并发 5 表示最多 5 条完整两阶段流水线，不是 5 个数字人任务外加 5 个
  SeedVR2 任务。
- 数字人明确终态失败后创建新的付费数字人尝试时，允许在本次勾选范围内重新选择健康账号；

  SeedVR2 单独重新选号。

  账号、不得重做数字人。仅下载失败继续使用原账号和原远程 ID。

## 1. 需求背景

新版工作台允许一次导入约 20～100 条甚至更多脚本。MiniMax 语音生成相对较快，真正的
吞吐瓶颈是 RunningHub 视频生成：

- 一个 RunningHub 账号当前最多同时执行 5 个任务；
- 一个视频子任务通常需要十几到二十分钟；
- 一条脚本可能因为音频超过分段上限而产生多个 RunningHub 视频子任务；
- 因此总工作量应按“视频子任务数”而不是“脚本行数”计算。

用户希望只使用新版工作台的业务账号登录和操作，但由服务器在后台同时调用多个互不相同的
RunningHub API 账号。正式资源池用户通常为管理员；当前另授权 `Cx_ceshi` 做受控测试。
所有任务、进度、结果和日志仍统一归属于当前登录业务账号在新版工作台中的项目，不因为实际
使用了哪个 RunningHub 账号而改变业务归属。

## 2. 已确认的产品需求

以下内容视为本轮已经确认，不再作为开放问题：

1. 多 RunningHub 账号调度只用于新版工作台 `/app/new`，旧网页和 `legacy_web` 永不进入。
2. 双池功能由云端全局开关和用户级授权共同控制，默认关闭；`Cx_ceshi` 是首个明确授权的
   测试账号。授权必须最终绑定不可变用户 ID，不使用硬编码用户名作为运行时权限判断。
3. 未获得双池授权的普通用户继续使用自己原有的一套 RunningHub 配置；除 `Cx_ceshi` 这项
   受控测试例外外，管理员资源池仍只向数字人网站 `is_admin=true` 的管理员开放。
4. 旧网页入口及其 `legacy_web` 任务不使用资源池；即使管理员从旧网页创建任务，也继续走
   原来的单账号逻辑。
5. 双池分支包含专用数字人账号池和专用 SeedVR2 账号池。资源池中的 RunningHub API Key
   由使用者保证来自不同真实账号；系统使用不可逆凭据指纹阻止池内和跨池重复计算容量。
6. 两个池分别累加各阶段的容量，当前每个真实 RunningHub 账号最大并发 5；数字人成功源视频
   持久化后释放数字人槽位，SeedVR2 再独立占用 SeedVR2 池槽位。
7. 管理员主要在晚上集中运行大批量任务，第一版不需要复杂的账号所有者优先级或抢占机制。
8. 无论哪个 RunningHub 账号实际执行，项目、脚本行、批次、视频、失败记录和下载结果都
   归新版工作台当前管理员账号。
9. 本功能只解决 RunningHub 视频生成资源池，不把多个 MiniMax 账号合并调度。现有“相同
   MiniMax API Key 共享自定义音色”保持原状。
10. 双池分支中，用户每次启动新版工作台 4A 时分别勾选本次允许使用的数字人账号和 SeedVR2
    账号。两组默认全选；余额不足、尚未充值或临时有特殊用途的账号可以在提交前取消勾选，
    取消勾选只影响本次生成，不删除账号，也不修改全局启用状态。
11. 当前同账号流程必须继续可用。项目级/批次级操作保存不可变执行模式，功能开关改变不得
    改变已经启动的任务使用哪个分支或执行账号。
12. SeedVR2 普通失败默认原账号重试；只有确认账号本身不可用于新尝试时才允许换到本次
    SeedVR2 快照内的其他健康账号。下载失败和提交结果不明确均不得换号重提。

## 3. 名词与归属关系

| 名词 | 含义 |
| --- | --- |
| 业务账号 | 登录新版工作台并拥有项目的数字人网站账号；通常为管理员，当前另含受控测试账号 `Cx_ceshi` |
| 数字人执行账号 | 数字人池中的真实 RunningHub API Key、Base URL、数字人工作流配置和并发上限 |
| SeedVR2 执行账号 | SeedVR2 池中的真实 RunningHub API Key、Base URL、SeedVR2 工作流配置和并发上限 |
| 数字人账号池 | 双池分支中专门执行数字人生成的一组 RunningHub 执行账号，即现有资源池的新职责 |
| SeedVR2 账号池 | 双池分支中专门执行 SeedVR2 放大的一组独立 RunningHub 执行账号 |
| 视频分段流水线 | 对应一个 `GenerationTask`；依次经过数字人和 SeedVR2 两个阶段，但在双池分支中两个阶段独立选号、独立计并发 |
| 远程阶段 | 流水线中的数字人生成或 SeedVR2 清晰化；每个阶段各自拥有远程任务 ID和状态 |
| 远程尝试 | 某个远程阶段向 RunningHub 实际提交的一次付费尝试，永久记录执行账号和远程任务 ID |
| 执行模式 | 4A 操作创建时锁定的 `same_account_v1` 或 `dual_pool_v1`，创建后不可改变 |

必须拆开两个概念：

- `owner_user_id`：任务和结果属于谁，始终是新版工作台当前登录的业务账号；
- `digital_human_execution_account_id`：数字人阶段实际使用的数字人池账号；
- `seedvr2_execution_account_id`：SeedVR2 阶段实际使用的 SeedVR2 池账号。

`same_account_v1` 为兼容现有字段和行为，两个阶段仍使用同一账号；`dual_pool_v1` 必须分别保存
两个阶段的账号绑定，不能用后一个阶段覆盖前一个阶段，也不能改变业务所有者。

不得为了借用其他 RunningHub Key，把任务的业务所有者临时改成其他网站用户。

## 4. 目标业务流程

```text
用户在新版工作台导入 20～100 条脚本
    -> 使用当前登录业务账号的现有 MiniMax 配置生成语音
    -> 用户审核声音并确认 RunningHub 费用
    -> 云端根据全局开关和用户授权锁定 same_account_v1 或 dual_pool_v1
    -> dual_pool_v1 分别确认数字人账号池和 SeedVR2 账号池的本次选择
    -> 工作台异步、幂等地启动所有待生成画面的脚本行
    -> 云端为每个音频分段创建独立视频子任务
    -> 数字人调度器从本次数字人快照选择并预留有空闲容量的账号
    -> 数字人结果下载、校验、持久化后释放数字人槽位
    -> SeedVR2 调度器从本次 SeedVR2 快照独立选择并预留账号
    -> SeedVR2 结果下载完成、最终失败或安全取消后释放 SeedVR2 槽位
    -> 原始片段、基础视频和最终状态统一回到当前登录业务账号的项目
```

开关关闭时，上述双池步骤由当前“一控多同账号”流程替代：`Cx_ceshi` 等已授权测试账号仍
读取并勾选现有数字人执行账号池，云端仍按这些真实账号分别计算 5×N 容量；每个视频分段一旦
选中 B/C 等执行账号，该分段的数字人与后续 SeedVR2 都严格使用同一个账号。它不是退回
`Cx_ceshi` 自己的单 RunningHub 配置。只有无资源池授权的普通用户才继续使用自己的单账号。
双池模式下，各阶段理论吞吐应按各自池的
账号数、单账号并发和阶段耗时分别测算，不能再把数字人与 SeedVR2 合并成一个“完整流水线
槽位”。例如某阶段有两个不同真实账号且每个并发 5，则该阶段理论容量为 10。

- 实际时间还要加上 RunningHub 排队、素材上传、结果下载、失败退避和基础视频合成时间；
- 任一阶段的池容量不足，都只限制该阶段，不应长期占用另一个池的槽位。

## 5. 功能范围

### 5.1 云端双资源池配置

资源池配置只保存在数字人云端服务，不能保存在浏览器或本地工作台。现有
`runninghub_execution_accounts` 在 `dual_pool_v1` 中作为数字人账号池；新增独立 SeedVR2
账号池。两个池中的每个账号至少包含：

- 稳定内部编号和池类型；
- 管理员可识别的备注名称；
- 加密保存的 API Key及不可逆 API Key 指纹；
- Base URL和本池对应工作流的 AI App ID；
- 最大并发数，当前限制为 1～5；
- 是否启用、健康检查结果、临时冷却状态；
- 创建、更新和最近使用时间。

工作流 ID 必须按账号和阶段校验，不能假定所有 API Key 都可访问同一个 AI App。数字人池只
支持 `digital_human`，SeedVR2 池只支持本项目固定的 SeedVR2 放大工作流；LTX 不在本轮范围。
同一真实 API Key 不能在任意一个池内或两个池之间重复注册并形成重复容量。

数字人网站管理员页面分别维护两个池的账号、Key、工作流和全局启用状态。当前同账号分支所用
账号不得因为新增 SeedVR2 池而被自动停用或删除。

双池分支在同一个 4A 费用确认区域显示两组安全摘要和复选框。每组均遵循：默认全选全局启用
且配置完整的账号；允许取消余额不足、未充值或临时有其他用途的账号；至少保留一个；只提交
内部 ID；本次选择不可变；下一次重新读取并默认全选。两组取消勾选都只影响本次操作，不修改
全局状态。

### 5.2 权限规则

是否进入双池分支由云端服务根据以下事实决定。全局开关由数字人网站管理员在
`/admin/runninghub-pool` 网页维护并持久化到数据库；环境变量只在网页首次保存前作为初始
默认值，不要求管理员通过 SSH 日常切换：

```text
网页“开启数字人账号池 + SeedVR2 独立账号池”开关=true
并且用户具有 dual_pool_v1 授权
并且批次 source_channel=new_workbench
并且工作流为本期支持的 digital_human
```

首个授权对象为网站用户 `Cx_ceshi`，但授权记录必须绑定用户 ID。除该受控测试例外外，新增
授权对象仍须 `is_admin=true`。请求体不得提供可伪造的 `use_pool=true`；未满足任一条件时，
新版工作台继续走当前 `same_account_v1`，旧网页、`legacy_web` 和历史任务永远不进入双池。

用户提交的数字人和 SeedVR2 账号 ID 列表均由云端逐项验证：账号存在、属于用户可用范围、
池类型正确、全局启用、配置完整且支持对应工作流。前端隐藏选项不是权限控制。

### 5.3 子任务级调度

资源分配单位是“视频分段的远程阶段”，不能把整个项目、批次或长脚本固定到一个账号。同一
分段的数字人阶段从数字人池选号；数字人源视频可靠持久化后，SeedVR2 阶段从 SeedVR2 池独立
选号。不同阶段可以使用不同账号。

建议调度规则：

1. 等待队列整体继续按视频子任务创建时间 FIFO。
2. 各阶段只从本次对应池已勾选，并且仍启用、配置完整、没有处于冷却状态的账号中选择。
3. 数字人池只统计数字人阶段的活动尝试；SeedVR2 池只统计 SeedVR2 阶段的活动尝试。
4. 同时参考本站已预留槽位和 RunningHub 返回的账号真实在途任务数。
5. 多个账号都有空位时，选择负载比例最低的账号：
   `(本站活动数或远程活动数的较大值 + 本轮预留数) / 最大并发数`。
6. 负载相同时使用稳定轮转或最近最少使用规则，避免总是压到第一个账号。
7. 数字人结果下载、校验并持久化后立即释放数字人槽位；SeedVR2 结果下载完成、该阶段最终
   失败或安全取消后释放 SeedVR2 槽位。某池全满只让对应阶段等待，不占用另一个池的槽位。
8. 某一个账号查询失败时，只暂停或冷却该账号，不得阻塞其他健康账号继续领取任务。

账号选择和本地槽位预留必须在数据库事务中原子完成，避免同一轮把多个任务同时分配到
同一个最后空闲槽位。虽然当前生产只有一个视频 Worker，也要保留重启和以后多 Worker 时的
一致性边界。

### 5.4 两阶段任务绑定、查询、取消和重试

- 每个数字人尝试记录数字人池账号，每个 SeedVR2 尝试记录 SeedVR2 池账号；一次尝试与其
  执行账号永久绑定。
- 两个阶段的查询、取消、状态恢复、结果下载和看门狗取消，必须使用各自尝试保存的原账号。
- 提交响应不明确时不能换账号重新提交，因为远端可能已创建并计费；同时保留保守容量占用。
- 确认尚未创建远程任务的上传前失败，可释放阶段账号并从该阶段本次快照重新选择。
- 数字人明确终态失败后的新付费尝试可从数字人快照重新选择健康账号，且完整保存尝试历史。
- 数字人成功后只复用其已保存的源视频，不要求 SeedVR2 继承数字人账号。
- SeedVR2 普通明确失败先在原 SeedVR2 账号创建新尝试；只有凭据失效、工作流无权限、账号
  禁止新尝试或达到账号级健康冷却阈值等确认账号不可用场景，才允许新付费尝试从本次
  SeedVR2 快照重新选健康账号。每次尝试都必须记录阶段、账号、远程 ID和失败/换号原因。
- 任一阶段仅下载失败时，继续使用原账号和原远程 ID，不重新生成或创建新付费任务。
- 服务重启后根据执行模式和尝试绑定恢复，不得按当前开关状态迁移分支或重新随机分配。

### 5.5 大批量 4A 启动可靠性

当前工作台 4A 启动会在一个 HTTP 请求中逐行上传图片并调用云端。20 条尚可能完成，接近
100 条时存在请求超时、用户重复点击和部分行已经创建、部分行未创建的问题。

因此本需求应同时包含以下配套改造：

- 用户点击“生成完整成片”后，工作台快速创建项目级/逐行操作记录并返回，不等待近百行
  全部完成云端启动；
- 项目级操作同时保存不可变执行模式；双池分支分别保存数字人账号 ID和 SeedVR2 账号 ID
  快照，所有脚本行和后续分段共用这两组快照；
- 后台协调器以受控并发逐行上传图片并调用云端 4A；
- 每一行使用稳定幂等键，重启或重复请求不会创建第二笔付费任务；
- 工作台重启后能够继续尚未完成的启动操作；
- 某一行启动失败只影响该行，其他行继续；
- 页面继续通过现有状态接口显示逐行排队、运行、合成、完成或失败；
- 该协调器只负责把任务可靠交给云端，RunningHub 的 5×N 并发仍统一由云端视频 Worker
  控制，工作台不能自己推算并直接绕过云端调度。

### 5.6 结果归属与新旧隔离

- `GenerationBatch.user_id`、`GenerationTask.user_id`、工作台 `Project.owner_user_id` 和
  本地素材目录继续使用当前登录业务账号。
- RunningHub 执行账号只作为内部执行信息，不改变接口鉴权和文件归属。
- 原始视频片段、`base_video`、4B 配方、普通成片和变体继续保存到当前登录业务账号的项目。
- 旧网页 `/batches` 和旧任务记录仍只显示 `legacy_web`，不能因为资源池改造而出现新版
  工作台批次。
- 其他用户不能通过任务编号、执行账号编号或下载地址读取当前业务账号的结果。

### 5.7 RH 币余额查询与新付费任务保护（步骤 17，待实施）

账号池必须能够回答“该执行账号还剩多少 RH 币、当前是否允许领取新的付费任务”。第一版只
接入 RunningHub 官方账户状态接口：

```http
POST /uc/openapi/accountStatus
Authorization: Bearer {API_KEY}
Content-Type: application/json

{"apikey":"{API_KEY}"}
```

本项目现有 Worker 已在付费提交前调用该接口读取 `currentTaskCounts`；步骤 17 应扩展同一次
响应的解析和持久化，不得为了每次提交再重复发送一笔相同的余额查询。第一版明确不接入仍被
官方标记为“开发中”的 `/openapi/v2/api-key/list`，不保存或展示 Key 独立限额、累计用量和
推算剩余额度。

#### 5.7.1 保存与展示范围

- 主要费用字段为 `remainCoins`，表示当前 API Key 所属 RunningHub 账户返回的剩余 RH 币；
  `remainMoney`、`currency`、`apiType` 和 `currentTaskCounts` 作为同一次响应的辅助状态保存。
- 金额、RH 币和后续可能出现的小数统一使用 Python `Decimal` 解析和计算，数据库使用不会经过
  `float` 的精确表示；不得把响应先转为浮点数或整数。
- 建议安全状态字段至少包含：`balance_status`、`remain_coins`、`remain_money`、`currency`、
  `api_type`、`remote_current_task_count`、`balance_checked_at`、`balance_error_code`、
  `balance_error_message`、`balance_retry_after`。
- 管理员资源池页面的数字人账号卡和 SeedVR2 账号卡均显示 RH 币、辅助钱包信息、状态和最近
  查询时间，并提供“刷新此账号”和“刷新全部余额”；页面不得显示完整 API Key、请求头、请求
  Body、凭据指纹全文或第三方完整响应。
- 新版工作台费用确认区可显示本次候选账号的安全余额摘要和数据更新时间，便于临时取消余额
  较少的账号；工作台仍只接收内部账号 ID和安全摘要，绝不接收完整 API Key。
- `accountStatus` 返回的是“该 Key 所属账户”的钱包状态。若同一 RunningHub 钱包下存在多个
  API Key，接口目前没有提供可依赖的钱包唯一 ID；因此不同账号卡显示的余额不得求和或宣称
  为多个独立钱包。

#### 5.7.2 状态与调度语义

余额状态至少区分：

- `UNKNOWN`：尚未成功查询，或成功响应缺少可解析的 `remainCoins`；
- `AVAILABLE`：RH 币高于账号配置的最低可派发阈值；
- `LOW`：仍允许派发，但低于管理员配置的预警阈值；
- `INSUFFICIENT`：达到或低于最低可派发阈值，暂停该账号领取新的付费任务；
- `AUTH_INVALID`：HTTP 401/403，或 RunningHub 明确返回 Key 无效、禁用或无权访问；
- `TEMPORARY_ERROR`：超时、网络错误、HTTP 429/5xx 或其他可重试的临时错误。

每个池账号应允许管理员配置非负的“RH 币预警阈值”和“最低可派发阈值”，且预警阈值不得低于
最低可派发阈值。第一版不根据任务时长猜测精确费用，也不做自动充值；它只依据 RunningHub
返回的 RH 币和管理员阈值决定能否开始下一次付费提交。

调度和恢复必须遵守：

1. 原子预留账号前跳过已缓存且仍在有效期内的 `INSUFFICIENT` 或 `AUTH_INVALID` 账号；同一
   操作快照内其他可用账号继续领取。
2. 实际付费提交前通过现有 `accountStatus` 容量检查同时刷新 RH 币。若此时确认余额不足且尚未
   创建远程任务，禁止调用付费提交接口，释放这次未付费预留并在本次不可变快照内重新调度。
3. 401/403 或明确 Key 无效时标记 `AUTH_INVALID` 并禁止新任务；不得自动删除账号或凭据。
4. 临时网络错误标记 `TEMPORARY_ERROR`、按退避时间重试并保留账号。余额查询失败不得被误判为
   余额为零，也不得修改全局启用状态。
5. 一旦已保存远程任务 ID，余额降低、查询失败或管理员阈值变化都不得迁移该尝试；查询、取消、
   下载和恢复继续使用原执行账号。余额保护只控制尚未付费的新提交。
6. 数字人池和 SeedVR2 池分别按各自账号状态过滤；一个池余额不足不能占用或停用另一个池账号。
7. 相同完整 API Key 若因历史兼容同时存在于旧 `runninghub_configs` 和数字人池，只按同一不可逆
   指纹缓存和限频一次查询结果，不能重复请求或展示为多份独立资金；不得使用第三方返回的脱敏
   Key 做本地精确匹配。
8. 余额结果使用短时缓存，后台按受控频率刷新；任务状态轮询不得触发余额请求。刷新任务需要
   单实例租约或等价幂等约束，避免 Web、Worker 重启或并行实例形成查询风暴。

#### 5.7.3 安全、失败降级与测试

- 完整 API Key 只在云端需要发起请求时解密，禁止下发浏览器、工作台、普通接口或诊断包。
- 日志只记录池类型、内部账号 ID、余额状态、脱敏错误码和查询时间；禁止记录 Authorization、
  `apikey` 请求字段、完整第三方响应或异常对象中可能包含的秘密。
- RunningHub 成功响应出现字段缺失、`null`、非十进制数、负数或超长值时安全降级为 `UNKNOWN`，
  不覆盖最后一次成功余额；同时记录独立的安全错误码，便于管理员判断数据是否过期。
- 自动化测试必须 mock `accountStatus`，覆盖整数/小数/字符串/null、余额正常/预警/不足、
  401/403、429、5xx、超时、无效 JSON、缓存命中、限频、重启恢复和不泄漏 API Key；不得调用
  真实 RunningHub 或产生费用。

## 6. 建议的数据结构方向

最终命名以实现时的现有模型风格为准，需求上至少要表达以下关系：

### 6.1 两类 RunningHub 执行账号

保留现有 `runninghub_execution_accounts` 作为数字人池实体；新增独立的 SeedVR2 执行账号
实体，例如 `seedvr2_execution_accounts`。两者都代表真实 RunningHub 账号，而非业务用户。
API Key 指纹必须做池内和跨池唯一性校验，避免一个真实账号被重复计算容量。

### 6.2 双池成员与双池功能授权

数字人池和 SeedVR2 池分别保存成员关系，表达“哪个业务用户可以使用哪些阶段账号”。另以
服务端用户级功能授权控制谁可以进入 `dual_pool_v1`。初始为 `Cx_ceshi` 授权，但数据库保存
用户 ID，不把用户名或账号 ID 硬编码到业务代码或前端。

### 6.3 视频任务与尝试绑定

`generation_tasks` 继续保留 `user_id` 作为业务所有者。为兼容 `same_account_v1` 保留当前
`execution_account_id` 语义；双池分支另行保存 SeedVR2 执行账号引用。数字人尝试和 SeedVR2
尝试分别记录每次尝试所用账号，不能只覆盖任务主表的当前账号，否则无法安全查询、取消、
下载和恢复旧远程任务，也无法审计确认账号不可用后的换号行为。

项目级/批次级或等价 4A 操作记录至少新增：执行模式、数字人账号 ID 快照、SeedVR2 账号 ID
快照。历史记录允许为空并按 `same_account_v1` 解释。SeedVR2 主记录和尝试新增可空的
SeedVR2 执行账号引用；新字段只由 `dual_pool_v1` 写入。

### 6.4 兼容现有配置

- 现有 `runninghub_configs` 和普通用户单账号行为暂时保留，不能破坏旧网页或普通用户。
- 新表和新字段使用新增 Alembic 迁移，不修改已发布迁移。
- 历史任务的执行账号字段允许为空，并按原用户配置恢复旧行为。
- 迁移不得重建被大量子表引用的父表，必须验证现有用户、批次、分段和任务数量不变。
- 不因新增双池自动停用、删除或改变现有执行账号；开关默认关闭，迁移后当前业务行为不变。
- 管理员页面可以提供“从现有用户 RunningHub 配置导入执行账号”的安全操作，避免回显
  现有 Key；也允许管理员重新输入一个新的独立 Key。

### 6.5 余额状态与凭据去重

步骤 17 使用新的安全 Alembic 迁移增加余额状态，不能修改步骤 1～16 已发布的迁移。由于历史
兼容允许同一个真实 API Key 同时存在于旧 `runninghub_configs` 和数字人池，账户查询缓存建议
按不可逆 `credential_fingerprint` 唯一保存，再由数字人池和 SeedVR2 池账号关联或按指纹读取；
不能在多个账号表各自形成互不一致的余额副本。

账号自己的预警阈值、最低可派发阈值和管理员备注仍属于池账号配置。共享查询结果不等于自动
合并、删除或改写旧配置，也不改变任务和文件所有权。迁移必须验证空库升级、现有数据升级、
外键检查以及历史重复指纹的安全读取，不危险地重建被任务和尝试表引用的父表。

## 7. 运行状态、日志与安全

资源池相关日志至少增加以下安全字段：

- `execution_mode`、`execution_pool_type` 和对应阶段的 `execution_account_id`；
- 执行账号备注名称；
- 账号最大并发和领取时的占用数；
- `remote_stage`，取值至少区分 `digital_human` 和 `seedvr2`；
- 选择、等待、冷却、恢复事件码；
- 远程尝试编号和 RunningHub 任务 ID；
- 既有 `source_channel`、`correlation_id`、业务用户、批次、脚本行和视频任务编号。

不得记录完整 API Key、解密后的凭据、完整脚本、素材内容或第三方完整原始响应。新版工作台
的 4A 费用确认必须明确显示当前是“一控多”还是“双池”，并显示本次候选账号；启动后每个
项目行必须显示云端实际分配结果。一控多按分段显示同一个“数字人 + SeedVR2”账号，双池按
分段分别显示数字人账号和 SeedVR2 账号。页面只显示安全备注名称与内部 ID，不显示 API Key、
凭据指纹、Base URL 或 App ID；管理员运维页和脱敏诊断包继续保留同样的安全定位字段。

资源池配置变更应记录审计事件：新增、启用、停用、并发修改、工作流 ID 修改和 Key 轮换。

## 8. 异常场景要求

| 场景 | 预期行为 |
| --- | --- |
| 一个阶段账号并发已满 | 继续使用该阶段快照内其他有空位账号；都满则该阶段本地等待，不占另一个池槽位 |
| 一个账号 Key 无效或工作流无权限 | 冷却/停用该账号并记录明确错误，其他账号继续 |
| RunningHub 真实在途数大于本站记录 | 以更保守的真实占用为准，不超发 |
| Worker 重启 | 原任务继续使用保存的执行账号查询，不重复提交 |
| 上传前明确失败 | 可释放绑定并换健康账号重试 |
| 提交结果不明确 | 保留原账号和状态，不跨账号盲目重提 |
| 数字人 RunningHub 明确失败 | 按现有退避进入新的数字人尝试；新尝试可在数字人快照内重新选账号并完整留痕 |
| 数字人成功 | 下载、校验并持久化源视频，释放数字人槽位；SeedVR2 随后从 SeedVR2 池独立调度 |
| SeedVR2 普通明确失败 | 原 SeedVR2 账号优先重试，复用数字人源视频，不重新生成数字人 |
| SeedVR2 账号确认不可用 | 新付费尝试可在本次 SeedVR2 快照内换健康账号，并记录不可用证据和换号原因 |
| 下载失败 | 使用原账号和远程 ID只重试下载 |
| 账号被管理员停用 | 不再领取本阶段新尝试；已有远程尝试仍使用原账号查询、取消和下载 |
| API Key 在任一池被误重复添加 | 根据凭据指纹跨池拒绝，不能把同一真实账号容量算两次 |
| 本次取消勾选某账号 | 本轮对应阶段不向该账号分配新任务，账号配置本身保持不变 |
| 任一池账号被全部取消勾选 | 双池 4A 禁止提交，并提示两个阶段都至少选择一个账号 |
| 启动后修改全局账号状态 | 不迁移既有远程任务；停用账号只停止领取新任务，仍可查询和下载已有任务 |
| 近百行启动中工作台重启 | 已启动行不重复计费，未启动行恢复继续 |
| 全局开关在任务运行中改变 | 已有操作按保存的执行模式完成，不迁移、换号或重提；只影响之后创建的新操作 |
| `Cx_ceshi` 有授权但全局开关关闭 | 继续显示现有一控多账号选择，只提交数字人池快照；每个分段的数字人与 SeedVR2 使用同一已分配账号，不退回个人单账号 |
| RH 币达到或低于最低可派发阈值 | 不向该账号发起新的付费提交；尚未付费的预留可释放并在本次快照内选择其他账号 |
| RH 币低于预警阈值但仍高于最低阈值 | 标记 `LOW` 并继续允许派发，管理员页面和费用确认区明确提示 |
| `accountStatus` 返回 401/403 或明确 Key 无效 | 标记 `AUTH_INVALID`，暂停新任务但不删除账号；已有远程任务仍用原账号完成后续操作 |
| `accountStatus` 超时、429、5xx 或网络错误 | 标记 `TEMPORARY_ERROR` 并退避重试，不按余额为零处理，不修改全局启用状态 |
| `remainCoins` 缺失、为 `null` 或格式异常 | 安全降级为 `UNKNOWN`，保留最后一次成功值和时间，不用异常值覆盖 |
| 多个本地配置使用同一真实 Key | 按不可逆指纹共享一次余额缓存与限频，不重复计算余额，不把相同钱包数值相加 |

## 9. 不在本轮范围内

- 除 `Cx_ceshi` 受控测试授权外，普通用户自行建立或共享 RunningHub 资源池；
- 多个 MiniMax 账号的语音任务负载均衡；
- LTX 对口型工作流使用资源池；
- 按部门、套餐、项目预算或精确预估单任务费用分配资源；
- 自动充值、自动购买 RH 币或根据余额预测可完成的视频条数；
- 接入仍标记“开发中”的 `/openapi/v2/api-key/list` 及 Key 独立额度管理；
- 管理员抢占正在运行的普通用户任务；
- 自动购买 RunningHub 额度或自动切换套餐；
- 修改旧网页任务记录和旧批次算法；
- 自动部署生产环境或自动写入生产账号数据库。

## 10. 验收标准

### 10.1 权限与隔离

1. 全局开关关闭时，`Cx_ceshi` 继续使用现有一控多资源池和单组费用确认，数字人与 SeedVR2
   严格绑定同一执行账号；无授权普通用户继续使用自己的单账号。
2. 全局开关开启且 `Cx_ceshi` 具有用户 ID授权时，可进入双池流程；其他无授权普通用户仍
   使用自己的原配置。新增其他双池授权对象默认仍要求 `is_admin=true`。
3. 双池费用确认区域分别默认勾选全部可用数字人和 SeedVR2 账号，用户可以取消任意账号。
4. 取消勾选的账号在本次对应阶段不会收到新任务，下一次新操作重新默认全选。
5. 任一池全部取消时不能提交；伪造、池类型错误、不属于可用范围或已停用的账号 ID 被拒绝。
6. 管理员从旧网页创建任务时不使用资源池。
7. 新版工作台任务不出现在旧网页任务记录中。
8. 无论实际执行账号是哪一个，所有结果只能由管理员项目读取。

### 10.2 并发与调度

1. 数字人池与 SeedVR2 池在 mock 环境中分别按各自真实 API Key和最大并发计算槽位。
2. 某阶段所有账号满载时，该阶段新任务保持等待，任一该阶段槽位释放后自动领取。
3. 一个账号满载或冷却时，同池其他健康账号继续领取，另一个阶段的池不受其槽位占用影响。
4. 同一 API Key 不能在池内或跨池重复提供虚假槽位。
5. FIFO 不因某个账号满载而阻塞其他可运行任务。
6. 数字人源视频下载、校验并持久化后释放数字人槽位；SeedVR2 独立预留和释放自己的槽位。

### 10.3 费用与恢复

1. 保存远程任务 ID 后，查询、取消、下载始终使用正确执行账号。
2. 模拟 Worker 重启不会重复提交。
3. 模拟提交响应不明确不会换账号重提。
4. 数字人明确失败后的新尝试可重新选账号，历史仍能指出每次尝试的阶段和执行账号。
5. 数字人成功后，SeedVR2 可选择 SeedVR2 池账号，不要求与数字人账号相同。
6. SeedVR2 普通失败优先原账号重试；只有模拟确认账号不可用时才换到 SeedVR2 快照内其他
   健康账号，并留下每次尝试和换号原因。
7. SeedVR2 失败或下载失败不会重新生成数字人；仅下载失败不会产生新的 RunningHub 付费
   任务。
8. 切换全局开关或撤销用户授权后，运行中操作仍按其不可变执行模式和原尝试账号恢复。
9. `accountStatus` 的 `remainCoins` 使用 `Decimal` 精确解析并按缓存频率保存；整数、小数和数字
   字符串均能处理，`null` 或异常格式安全降级且不覆盖最后一次成功值。
10. RH 币不足或 Key 无效的账号不会收到新的付费提交，同一快照内其他账号可继续；已经保存
    远程任务 ID的尝试不迁移账号。
11. 临时余额查询错误只触发退避，不自动停用或删除账号；工作台任务轮询不会产生余额查询风暴。

    Authorization、`apikey` 请求字段或第三方完整响应。

### 10.4 大批量工作台

1. 100 条脚本行的 4A 启动请求能快速返回并进入后台处理，不依赖单次长 HTTP 请求完成。
2. 中途关闭并重启工作台后，未完成启动的行可以恢复。
3. 重复点击或网络重试不会为已启动行创建重复付费任务。
4. 单行失败不阻断其余行，页面能准确显示成功、运行、等待和失败数量。
5. 费用确认明确显示“一控多/双池”和候选账号；启动后每行按分段显示实际账号，未完成原子
   预留的阶段显示“待分配”，工作台重启后仍能从持久化操作记录恢复显示。

### 10.5 迁移与回归

1. 空数据库和包含现有用户、批次、分段、任务的数据库均能升级。
2. 历史任务、旧网页、普通用户单账号、取消、看门狗和下载测试保持通过。

5. 迁移本身不启用双池、不停用现有账号；开关关闭时通过完整当前流程回归。

## 12. 已确认的方案选择

1. 第一版资源池只支持 `digital_human` 和其后的 SeedVR2 放大，不支持 LTX。
2. 当前一控多同账号流程继续保留；双池只由默认关闭的网页服务端开关和用户授权进入。网页
   开关保存到数据库，环境变量只作为首次保存前的默认值。
3. `Cx_ceshi` 是首个双池测试授权账号，权限持久化按用户 ID实现，不硬编码用户名。
4. 当前资源池在双池分支中专门做数字人；新增普通 RunningHub 池专门做 SeedVR2。
5. 双池费用确认使用两组默认全选账号列表即可，不另做复杂的计费 UI。
6. SeedVR2 普通失败原账号优先重试；确认账号不可用时可以换号；同一次远程尝试、模糊提交
   和下载重试永远绑定原账号。
7. 第一版不做账号优先级；相同真实 API Key 在旧配置、数字人池或 SeedVR2 池中出现时，共同
   遵守该真实账号的并发上限，不允许重复计算容量。
8. 账号池费用管理第一版只使用 `accountStatus`，以 `remainCoins` 为主要判断值；
   `remainMoney/currency/apiType/currentTaskCounts` 作为辅助信息。暂不接入 `api-key/list`。
9. 管理员为每个池账号配置 RH 币预警阈值和最低可派发阈值；余额保护只阻止尚未付费的新提交，
   不迁移已保存远程任务 ID的数字人或 SeedVR2 尝试。
